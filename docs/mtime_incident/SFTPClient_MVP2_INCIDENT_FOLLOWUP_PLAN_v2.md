## 1. 인시던트 문서 ↔ HEAD 소스 대조 결과 `[확정]`

| # | 인시던트 주장 | 코드 실물 | 판정 |
|---|---|---|---|
| 1 | unchanged 판정 = `size == && mtime ==` (runner.go) | `exists && k.Size == e.Size && k.MTime == mtime` 그대로. 카테고리 무관 동일 적용 | 일치. 코드는 설계대로 동작, 버그 아님 |
| 2 | `internal/logging` 부재, 표준 `log` → stderr 전용 | 패키지 없음. `cmd/rinexclient/main.go` 표준 `log`만 사용 | 일치 |

| 4 | 해시 판정에 스키마 변경 필요 | schema v5에 `content_hash` 없음 → v6 마이그레이션 선결 | 일치 |

### 1.1 코드 대조로 새로 확인된 사실 — RNX3 hung 메커니즘 `[확정]`

`transport/sftpfs.go`:

- `dialTimeout`(10s)은 TCP 연결 + SSH handshake까지만 적용. handshake 직후
  `SetDeadline(time.Time{})`으로 데드라인 **해제**.
- SSH keepalive 없음.
- `UploadPart`는 청크 **사이**에서만 ctx 확인 → 진행 중인 SFTP Write 하나가
  네트워크 스톨로 블록되면 해당 고루틴 무한 대기.
- `main.go`는 `signal.NotifyContext`뿐, 실행 전체 watchdog 없음.

→ "0바이트 `.part` 25분 잔류"는 이 조합으로 재현 가능한 현상이다. 전송 미완료
→ VERIFIED 전이 불가 → 그 사이 mtime 폭풍이 revision을 올려 rev≈24 누적
(산술 정합).

> **[정정 2026-09-18]** 위 코드 사실 4개(데드라인 해제·keepalive 부재·청크 중
> ctx 미확인·watchdog 부재)는 그대로 `[확정]`이다. 그러나 "25분 `.part` 잔류가
> 이 취약점의 관측 증거"라는 결론은 **철회**한다 — 당시 SFTPClient가 약 25분간
> 꺼져 있었다는 사실이 확인됐다(§6.1). rev≈24 누적 자체는 mtime 폭풍만으로
> 설명되므로 산술 정합은 유지된다.

### 1.2 연결 공유 구조 `[확정]`

`main.go`는 `DialSFTP` 1회로 만든 단일 `SFTPFS`(ssh.Client 1 + sftp.Client 1)를
Uploader로 전달하고, MaxWorkers개 워커가 이를 **공유**한다.
→ 연결 데드라인은 연결 전체에 걸리고, watchdog이 연결을 닫으면 모든 워커가
동반 실패한다. 유닛 3(스톨 방어) 정책 결정의 전제 사실.
*(정정 2026-09-18: 구 순서 표기 "유닛 2" → 현행 순서 "유닛 3")*

## 2. 교차검증(GPT) 4개 지적 — 검수 판정

**총평: 4개 모두 타당, 수용.** 아래 보완 사항과 함께 각 유닛 설계에 반영한다.

### 2.1 "이전 해시 확보" — 수용 (설계 빈틈이었음)

"애매할 때만 해시"는 비교할 기준 지문이 있어야 성립한다. 확정 흐름:

- **신규 파일:** 최초 등록 시 해시 저장.
- **실제 변경(새 revision):** 새 revision의 해시 저장.
- **기존 v5 행의 자연 백필:** `size= · mtime=`(unchanged 판정 통과) 시 해시를
  계산해 저장. 안전 근거 — "size=·mtime=이면 내용 동일"은 현행 unchanged
  판정이 이미 서 있는 신뢰 기반이므로 **새 가정을 도입하지 않는다**.
- **해시 없는 행이 mtime 드리프트를 먼저 만난 경우:** 판별 근거가 없으므로
  1회 보수적으로 새 revision 처리(전송) + 지문 기록. 이후부터 방어 작동.
  (백필 과거분을 조용히 누락시키지 않는 보수적 선택 — 누락 > 헛전송)

**보완(검수자 추가): 백필 상각.** 측위원 common_ledger 11만 행 이상 — 첫 실행
전량 백필은 수십 GB 로컬 읽기가 한 회차에 몰린다. **`MaxHashBackfillPerRun`
상한으로 회차 분할 상각**한다. 상한 기본값과 근거는 해시 유닛(현행 순서
유닛 2) 설계문에서 확정. *(이행됨: 기본값 500 — UNIT2_HASH_DESIGN_v3 §3.1)*

### 2.2 `MetadataChangedOnly` + mtime 갱신 — 수용

해시 같고 mtime만 다른 경우 장부 mtime을 현재 값으로 갱신하지 않으면
**같은 파일을 매 실행 반복 해시**한다. 판정 결과를 3분화:

| 결과 | revision | state | mtime | 후보 | 관측 |
|---|---|---|---|---|---|
| `Unchanged` | 유지 | 유지 | 유지 | 아니오 | unchanged 집계 |
| `ContentChanged` | +1 | CHANGED | 갱신 | 예 | changed 집계 |
| `MetadataChangedOnly` | 유지 | **유지** | **갱신** | **아니오** | 별도 집계(§2.3) |

**보완(검수자 추가) 2건 — 해시 유닛(현행 순서 유닛 2) 설계문 필수 기록 사항:**
*(이행 상태 2026-09-18: 2번의 origin 제외 적용 순서는 UNIT2 v3 §4.4에서 확정.
1번의 LEDGER_CONCEPT 명문화 완료 여부는 확인 필요 — 유닛 2 잔여 리뷰 시 점검)*

1. **mtime 컬럼의 의미 재정의.** "마지막 전송 시점의 관측 사실" →
   "**변경 판정 기준선**"으로 주인이 바뀐다. "하나의 사실에 하나의 주인"
   원칙상 스키마 주석과 LEDGER_CONCEPT에 명문화하여 재론을 막는다.
2. **DOWNLOAD-origin 분기 적용 여부.** `runner.go`의 DOWNLOAD-origin 제외
   분기도 동일한 `k.MTime == mtime` 비교를 쓴다. metadata-only 갱신을 이
   분기에 적용하지 않으면 origin=DOWNLOAD 파일이 mtime 드리프트 시 매 회차
   재검증된다. 적용 여부와 근거를 유닛 3 설계 범위에 포함한다.

### 2.3 경보 이원화 — 수용

해시 방어 적용 후 mtime 폭풍은 CHANGED가 아니라 `MetadataChangedOnly`로
흡수되므로, CHANGED 폭주 경보만으로는 상류 이상을 볼 수 없다.

- **`content_changed` 폭주** — 실제 내용 변경 대량 발생.
- **`mtime_drift_suppressed` 폭주** — 내용 동일·mtime 대량 변경, 재전송 억제.
  → "전송 피해는 막았으나 상류에서 잘못된 복사 작업 발생"의 관측 신호.
  방어가 장애 흔적까지 숨기지 않는다.

### 2.4 스톨 방어 정책 선결 — 수용 (전제 사실 §1.2로 확인)

"deadline + keepalive + watchdog" 단어만으로 구현하지 않는다. 유닛 3(스톨 방어)
설계문에서 다음을 먼저 확정한다
*(정정 2026-09-18: 구 순서 표기 "유닛 2" → 현행 순서 "유닛 3". 유닛 성격
재정의는 §6.1·§6.6 참조 — 기존 5문항에 재시도 예산 문항 추가)*:

1. 스톨 시 실행 전체 실패 후 다음 스케줄 재시도 vs 부분 계속
2. 워커별 독립 SFTP 연결 vs 공유 연결 유지
3. 공유 유지 시 연결 단위 watchdog의 폐기 범위(동반 실패 허용 여부)
4. SSH keepalive 실패 횟수와 작업 타임아웃의 구분
5. 연결 강제 종료 후 IN_PROGRESS → FAILED 확정 절차
6. 연결·환경 장애 및 공유 연결의 동반 실패가 파일별 attempts 예산을
   소모해야 하는가. 예산 소진 시 관측·복구 정책까지 확정 (§6.8).

**제약(검수자 추가):** 설계안 12.3이 "연결 방식(단일 연결 다중 세션 vs 워커별
연결)은 MVP4 벤치마크 후 확정"으로 미뤄둔 항목과 겹친다. 유닛 3의 결정은
MVP4 측정과 충돌하지 않는 **안전장치 범위로 한정**한다 — 성능 선택을
선점하지 않는다.

## 4. 신규 관측 (2026-09-17, 구두) `[관측-미검증]`

**측위원 V3(RNX3) 시간 단위 파일이 정상 운영 중이다.**

파급 — 인시던트 §10-3 가설 재평가:

- "중복/재도착 파일이 QC 오류를 일으킨다"는 논리(가설 4, H1 계열)는
  **무력화**된다. 시간 파일도 재전송 폭풍을 동일하게 맞았는데 정상이라면,
  재도착 자체가 QC 격리의 원인이 아니다.
  > **[재평가 2026-09-18]** 이 무력화의 전제("시간 파일 정상")는 방문 직후
  > 시점의 관측이었다. §6.2의 신규 관측(14~16일 시간데이터 공백처럼 표시 →

## 6. 신규 관측·재해석 (2026-09-18 세션)

### 6.1 "25분 `.part` 잔류" 재해석 — 유닛 3 성격 변경 `[관측-미검증]`

**신규 사실 (구두, 기억 기반):** 2026-09-16 현장 방문 시 기존 스케줄러와의
충돌을 우려해 스케줄러를 끄고 SFTPClient를 수동 실행하는 과정에서 정리가
꼬여 **중복 운영 상태**가 됐고, 그 과정에서 SFTPClient가 **약 25분간 꺼져
있었다.** 관측된 0바이트 `.part` 25분 잔류는 이 실행 중단의 정상 잔여물이며,
시작 시 IN_PROGRESS 복구 절차가 처리하는 설계 내 시나리오다. **네트워크
스톨의 관측 증거가 아니다.**

**파급:**

- §1.1의 코드 취약점 4개(데드라인 해제, keepalive 부재, 청크 중 ctx 미확인,
  watchdog 부재)는 코드 실물 대조 결과이므로 그대로 `[확정]`이다.
- 그러나 유닛 3의 성격이 바뀐다: **"관측된 장애의 재발 방지" → "코드 대조로
  확인된 취약점의 예방 조치."** 현장에서 스톨이 실제 발생했다는 증거는 현재
  없다.
- 설계 판단에의 반영: 관측 장애가 없으므로 공격적 구조 변경(예: 워커별 독립
  연결 전환)보다 **보수적 안전장치(작업 타임아웃 + keepalive + 감지 시
  IN_PROGRESS → FAILED 확정)** 쪽에 무게가 실린다. §2.4의 MVP4 비선점
  제약과도 방향이 일치한다.

### 6.2 QC error 폴더 격리 관측 — 가설 4 복귀 `[관측-미검증]`

**신규 사실 (구두, 기억 기반):**

- 2026-09-14 확인 시 **최신 일데이터까지 도착해 있었으나, QC 처리에서 error
  폴더에 격리**되어 있었다. 확인 위치는 기관 현장이 아니라 **지리원 데이터가
  도착하는 사내 수신 컴퓨터**다. *(v2에서 확정 — v1의 "기관 표기 확인 필요"
  플래그 해소)*
- gnssdata 기준 측위원 시간데이터가 **9/14~9/16 구간 공백처럼 표시**되다가
  **9/17부터 재개**됐다. 서울시 일·시간데이터는 정상 유입 중.
- rev≈24 폭주 관측(9/15)이 "재도착 → QC 격리" 의심의 출발점이었다.

**해석(가설, 미검증):** 해당 구간의 "데이터 없음"은 미도착이 아니라
**격리**다. 인과 사슬: `rinexSend` mtime 리셋 → SFTPClient 재전송 폭주(rev↑)
→ 수신 QC가 동일 파일의 반복 재도착을 이상으로 판정, error 폴더 격리 →
gnssdata에 미표시. 이 사슬이 맞다면 SFTPClient는 설계대로 동작했고("변경
관측 → 재전송"), 근본 원인은 상류 mtime 리셋이며, **유닛 2(해시 판정)가
정확히 이 사슬의 시작점을 끊는다.**

**§4 재평가:** §4(9/17)의 가설 4 무력화는 "시간 파일 정상" 전제 위의
판정이었다. 위 관측이 맞다면 시간 파일도 격리를 겪었으므로 전제가 무너지고
**가설 4(재도착 → QC 격리)가 주범 후보로 복귀**한다.

**후속 관측 (2026-09-18 당일 추가) `[관측-미검증]`:** 측위원 **일단위
데이터도 정상 유입이 재개**됐다. QC 프로그램이 수정된 것으로 **추정**된다
(동료 개발 영역, 수정 사실·내용 미확인). 격리로 막혀 있다가 QC 측 변경으로
통과가 재개된 그림이므로 위 격리 가설을 지지하는 정황이다.

단, 이것은 **증상의 해소이지 원인의 제거가 아니다.** 상류 `rinexSend`의
mtime 리셋은 계속되고 있고 유닛 2는 미배포 상태이므로, SFTPClient의 재전송
폭주는 지금도 지속 중일 가능성이 높다 — QC가 이제 그것을 흡수할 뿐이다.
근본 차단은 10월 유닛 2 배포가 담당하며, "QC 수정 이후에도 폭주가
계속됐는가"는 §3.1 체크리스트의 rev 추이 쿼리로 사후 확인한다.

**미해결 질문 (원격 확인 불가로 보류):**

- 왜 9/17부터 통과가 재개됐는가 — (a) 16일 정리로 중복 운영이 해소되어
  재도착 빈도가 QC 허용 범위 아래로 하락, (b) 꼬였던 운영 상태 자체의 해소,
  (c) QC 측 수정(위 후속 관측 — 일단위 재개 시점과의 선후 관계 미확인).
- QC 내부 로직은 동료 개발 영역으로 현재 확인 불가. error 폴더 실물·거절
  사유 로그·중복 유입 흔적 확인은 §3.1 체크리스트 1번으로 이관.
- 격리분은 유닛 2를 배포해도 저절로 복구되지 않는다. 재처리 절차는 QC 측과
  협의가 필요하다.

### 6.3 `.filepart` — HEAD 대조 `[확정]` + 현장 관측 `[관측-미검증]`

**현장 관측 (구두, 기억 기반 — 사진·건수 기록 없음):** 당시 전체 파일 중
2~3개 수준의 `.filepart` 파일이 있었고, db 조회 시 등록 흔적을 본 기억이
있다. 기억의 확실성은 낮으나, ledger는 영속 기록이므로 §3.1 체크리스트
2번의 쿼리로 사후 확정 가능하다.

**HEAD 대조 결과 `[확정]` (2026-09-18):**

- SFTPClient는 `.filepart`를 **생성할 수 없다.** `internal/domain/filename.go`
  의 임시 접미사는 `partSuffix = ".part"` 단일 상수다. 따라서 출처는
  SFTPClient 실행 오류가 아니라 **외부 도구**다. `.filepart`는 WinSCP 계열의
  기본 임시 접미사이므로 `rinexSend`의 WinSCP 사용 여부 확인이 필요하다
  (16일 중복 운영 꼬임 중 해당 전송이 중단됐다면 시점도 정합).
- `.filepart`는 파이프라인을 **통과한다:** ① 문자열상 `.part`로 끝나지
  않으므로 `IsPartFile` 미해당, `NormalizeName`의 TrimSuffix에도 걸리지
  않는다. ② 버려진 파일은 mtime이 오래돼 Grace 통과, size > 0이면 Zero 검사
  통과. ③ RINEX3 긴 이름의 `MatchesName`은 주기 필드(`01d`/`01h`)만
  보수적으로 대조하므로 `..._01h_..._.rnx.filepart`가 **CategoryMatchOK로
  통과**하고, RINEX2 짧은 이름도 확정 Mismatch가 아니면 Unknown 유보로
  통과한다.
- 결과: 버려진 `.filepart`가 자기 자신의 file_name으로 장부에 등록되어 전송
  후보가 되고, **불완전한 파일이 그 이름 그대로 기관 서버에 업로드될 수
  있다.** 유닛 5의 결과 심각도가 "임시 파일 잔류"가 아니라 "손상 파일
  전달"이므로 **중요도를 상향**한다.

### 6.4 기각된 가설 기록 (재론 방지) `[기각]`

**lock 영구 점유 가설:** "14일부터 스톨된 인스턴스가 lock을 계속 쥐어 후속
실행이 전부 `lock.ErrHeld` 정상 종료(0)로 빠지고 전송이 정지됐다"는 가설은
9/14에 최신 일데이터의 **도착이 확인**된 사실과 모순되어 기각한다. 전송
파이프라인은 살아 있었다.

단, 이 가설 검토 중 드러난 관측 공백은 유효하다: **lock 점유 시 후속 실행이
경보 없이 정상 종료(0)하므로, 장기 점유가 발생해도 신호가 없다.** 이는 기존
설계의 의도된 동작(UNIT2 v3 §5)이나, 무경보라는 점은 유닛 4(경보 이원화)
범위 검토 시 후보 항목으로 올린다 — 결정이 아니라 검토 후보다.

### 6.5 추가 논의 — 수정 목적과 진행 순서 `[합의]`

- **사용자가 전달한 현재 이해:** QC 프로그램이 중복 전송을 유연하게 받아들여
  데이터 유입이 재개됐다. 이것과 별개로, 내용이 같은 파일의 불필요한 중복
  전송은 SFTPClient에서 수정해야 할 문제다. QC의 수용 개선을 송신 문제의
  해결로 취급하지 않는다. QC 내부 변경·로그는 이번 작업에서 독립 검증하지 않았다.
- §6.2는 당시 가설 이력으로 보존한다. 현재도 mtime 리셋이나 재전송 폭주가
  지속된다는 단정은 최신 실물 확인을 대신하지 못한다. rev≈24만으로 전송 성공
  횟수나 QC 거절 원인을 확정하지 않는다.
- **남은 진행 순서: 유닛 5 → 유닛 3 → 유닛 4 → 배포 준비.** 기존 번호는
  유지한다. 유닛 5는 문서상 코드 대조로 드러난 미완성 파일 통과 문제이며
  범위가 작아 먼저 닫는다. 실제 현장 전송 여부는 별도 확인 사항이다.
- 유닛 5의 범위는 `.part`·`.filepart`를 임시 파일로 인식하여 후보에서
  제외하는 것과 이름 정규화·IdentityRule 영향 검토다. 접미사를 지웠다는
  이유로 미완성 파일을 완성 파일로 취급하면 안 된다. 기존 장부·원격 파일의
  삭제나 정리는 이번 합의에 포함하지 않고 현장 확인 후 별도 판단한다.
- `[관측-미검증]`은 사용자가 직접 보지 않았다는 뜻이 아니다. 현장 목격 또는
  구두 전달은 있으나 사진·로그가 부족해 세부 사항과 인과관계를 재검증하지
  못했다는 뜻이다. AI가 직접 확인한 코드 사실과 구분한다.

### 6.6 유닛 3의 근거 이력과 신규 기관 관측

1. **최초(9/17):** 측위원의 25분 `.part` 잔류를 스톨로 해석하여 재발 방지를
   추진했다. 이 현장 원인 해석은 §6.1에서 철회됐다.
2. **9/18 재해석:** 실행 중단이라는 기억을 반영하여, 실제 스톨의 관측 증거
   없이 코드에서 확인된 무한 대기 가능성을 보완하는 예방 조치로 정리했다.
3. **추가 논의:** 차기 리눅스 기관의 BNC 통신 불안정 관측이 운영상 근거로
   추가되어, 유닛 3을 다음 기관 배포 전에 갖출 안전장치로 중요도를 높였다.
   측위원 스톨 가설을 되살린 것이 아니다.

**신규 기관 `[관측-미검증]`:** 사용자 전달에 따르면 사무실에서는 정상인 BNC
수신 데이터가 해당 기관에서는 중간중간 끊기며, 시간 파일에 공백이 생긴다.
BNC 로그·현장 네트워크 설정·SFTP 재현 결과는 이번 논의에서 확인하지 않았다.
방화벽 원인, idle 타임아웃, 세션의 무응답 단절 및 SFTP에서도 같은 증상이
발생하는지는 모두 미확인이다. 반복 SFTP 스톨을 상시 확정 조건으로 쓰지 않는다.

**설계 근거:** 코드상 무한 대기 가능성을 보완하며, 신규 기관 관측은 그
우선순위를 높이는 추가 근거로 사용한다. BNC 증상만으로 패킷 유실·순간 단절·
DPI 간섭 중 어느 하나를 원인으로 선택하지 않는다. 연속 스트림이라는 설명만으로
idle 관련 정책을 완전히 배제하지도 않는다.

keepalive는 연결 상태 감지와 일부 환경에서의 유휴 연결 유지 효과를 검토하는
수단이다. 방화벽 정책을 우회하거나 순간 단절을 예방한다고 보장하지 않는다.
구체적인 방식·간격·실패 횟수는 미결이며, 파일 작업의 진전과 연결 응답을
구분하여 무진행 감지·복구에 설계의 무게를 둔다.

### 6.7 유닛 3 설계 원칙과 미결 항목

**합의 원칙: 느리고 일시적으로 끊기는 회선에서도 정상 전송에 지장을 최소화하는
안전장치.** 단순 총 소요시간만으로 정상 대용량 Daily 전송을 실패시키지 않는다.

- **진행 기준:** 작업별 쓰기 완료와 마지막 진행 시각 등을 관측하는 방향을
  검토한다. SSH 응답이 있다고 파일 작업도 진행 중인 것은 아니다. 다른 워커의
  진전이 멈춘 워커를 가리지 않아야 한다. 업로드뿐 아니라 원격 확인·이름 변경
  등 블록 가능한 작업도 포함해 관측 지점과 무응답 제한을 설계한다.
- **중단 범위:** 공유 연결 유지가 현재 권고 방향이나 최종 정책은 미확정이다.
  연결 강제 종료는 정상 진행 중인 다른 워커까지 영향을 줄 수 있다. 신규 착수
  중지, 미완료 작업의 실패 확정, 동반 실패 식별과 예산 처리를 함께 결정한다.
- **종료 후 상태:** 통신 실패로 common revision을 올리지 않는다. 같은 revision의
  put 상태와 시도 이력으로 처리한다. 취소된 context 때문에 실패 기록까지
  취소되지 않도록 종료 순서·기록용 context 수명과 복구 경로를 설계한다.
- **부분 성공 보존:** 이미 VERIFIED인 현재 revision은 내용이 바뀌지 않는 한
  연결 장애 때문에 재전송하지 않는다. 그러나 작은 파일의 부분 성공이 대용량
  파일의 완료까지 보장하지는 않는다. 매번 중간에 끊기는 파일의 반복 실패와
  예산 소진도 검증 시나리오에 포함한다. 전송 재개 기능 채택은 아직 결정하지 않았다.
- **미결:** 시간값, keepalive·watchdog 조합, 회차 내 재연결·재시도 및 간격은
  아직 확정하지 않는다. 선택지·트레이드오프·권고안 검토 후 구현한다.

**MVP4 경계:** 같은 공유 연결을 끊김 후 다시 맺는 것은 워커별 연결 구조로
전환하는 것과 다르므로 검토 가능하다. 다만 현재 `internal/ledger/put.go`는
회차 내 동일 파일 재시도 없이 다음 스케줄에서 재시도하는 정책이다. 회차 내
재연결을 채택한다면 남은 미착수 파일을 위한 재연결인지, 실패 파일의 동일 회차
재시도까지 허용하는지 구분하고 기존 정책 변경을 명시해야 한다.

### 6.8 attempts 예산 — 유닛 3 핵심 결정 항목

**코드 확인(이번 문서 갱신):** `internal/ledger/put.go`의 `BeginPut`은 성공 시
attempts를 1 증가시킨다. `MaxRetries`는 최초 착수를 포함한 동일 revision의
누적 자동 시도 상한이다. `internal/put/runner.go`는 FAILED의 attempts가
상한 이상이면 자동 후보에서 제외하고, exhausted 집계 및 WARN을 출력한다.
따라서 이를 무조건 "영구 제외" 또는 "조용한 누락"이라고 표현하지 않는다.
정확한 위험은 **동일 revision의 자동 재시도가 소진되어 미전송 상태가 남는 것**이다.

스톨 전에 BeginPut이 성공했다면 이미 예산을 소비한 상태다. 공유 연결 종료로
함께 실패한 작업도 착수에 성공했다면 예산을 소비한다. 종료 순간에 추가로
attempts를 올리는 것은 아니며, 미착수 작업까지 일괄 차감한다고 해석하지 않는다.

**설계에서 반드시 결정할 질문:**

1. 파일 자체의 실패와 연결·환경 장애 및 동반 취소를 어떤 근거로 구분할 것인가.
2. 환경 장애도 현재와 같은 파일별 예산을 사용할지, 별도 제한·복구 정책을 둘지.
   attempts는 실제 착수 이력이므로 단순 차감·초기화를 확정안으로 삼지 않는다.
3. 공유 연결 실패를 감지한 뒤 새 작업 착수를 어떻게 막아 불필요한 예산 소모를
   제한할 것인가. 회차 내 재연결을 넣으면 시도 횟수와 대기시간을 어떻게 제한할 것인가.
4. 상한 소진을 운영자가 확인하고 복구하는 절차는 무엇인가. 기존 WARN·집계의
   충분성을 평가하며, 추가 경보는 유닛 4와 경계를 정한다.

예산 정책은 이번 논의에서 확정하지 않았다. 무제한 재시도도 자동 채택하지 않는다.
반복 장애·동반 실패·대용량 파일의 소진·완료 파일 보존을 함께 검증하여,
"감지 후 종료"가 장기적인 전송 포기로 이어지지 않도록 설계한다.
