# SFTPClient — 유닛 1 설계 확정문: internal/logging

- **작성일:** 2026-09-17
- **선행 문서:** `SFTPClient_MVP2_INCIDENT_FOLLOWUP_PLAN.md` §3 순서 1,
  설계안 14 (로그 정책), 인시던트 §7-1
- **범위:** 파일 로깅 신설과 배선. 로그 **내용**(어떤 이벤트를 어떤 수준으로
  남길지)의 확장은 이 유닛의 범위가 아니다 — 기존 출력을 파일에 보존하는
  것이 목표다. 내용 확장은 순서 4(경보 이원화)에서 필요한 만큼만 한다.

---

## 0. 현황 `[확정 — 2026-09-17 HEAD 대조]`

- `internal/logging` 패키지 부재. 코드 어디에도 로그 파일을 여는 곳이 없다.
- config 에 `LogDir` 류 키 없음. 배포 폴더의 `logs\` 는 자리표시자일 뿐이다.
- 모든 출력은 표준 `log` → stderr. 스케줄러 실행에서는 보존되지 않는다
  (이번 인시던트 추적 불능의 직접 원인).
- 호출부 구조:
  - `put`: `Runner.Logger *log.Logger` 주입, nil 이면 `log.Default()`.
    내부는 `r.logf` 로 단일화되어 있다.
  - `plan.go`: `RunReport.Print(l *log.Logger)`, nil 이면 `log.Default()`.
  - `ledger/db.go:357`: `log.Printf` 직접 호출 1건 (마이그레이션 공지).
  - `cmd/rinexclient/main.go`: `log.Printf` 다수.

→ **모든 경로가 표준 `log` 로 수렴한다.** 출력 대상만 바꾸면 호출부 수정이
0건이다. 이 사실이 본 설계의 토대다.

---

## 1. 완료 기준

1. **실행하면 로그 파일이 실제로 생성된다.** 수동 실행과 스케줄러 실행 모두
   `logs\rinexclient_YYYYMMDD.log` 에 같은 내용이 남는다.
2. 콘솔(stderr) 출력은 종전대로 병행된다 — 수동 실행 시 화면에서 바로 본다.
3. 일자별 파일 분리. 자정을 넘긴 첫 기록부터 새 날짜 파일에 쓴다.
4. 보존일(`LogRetentionDays`, 기본 30) 초과 파일은 자동 삭제된다.
5. 강제 종료(스케줄러 kill, 크래시) 직전까지의 줄이 파일에 남아 있다.
6. 병렬 워커의 동시 기록에서 줄이 섞이지 않는다 (`-race` 통과).
7. 파일 로깅이 불가능한 환경에서도 프로그램은 전송을 계속한다 (§4).

## 2. 구조 확정

### 2.1 패키지: `internal/logging` — 회전 Writer 하나

```go
// RotatingWriter 는 io.Writer 다. Write 마다 로컬 날짜를 확인해
// 날짜가 바뀌었으면 새 파일(rinexclient_YYYYMMDD.log)로 전환하고,
// 전환 시점에 보존일 초과 파일을 삭제한다.
func NewRotatingWriter(dir string, retentionDays int) (*RotatingWriter, error)
func (w *RotatingWriter) Write(p []byte) (int, error)
func (w *RotatingWriter) Close() error
```

책임은 셋뿐이다: 파일 열기/전환, 보존 삭제, Write 직렬화(mutex).
포맷·수준·필터는 책임이 아니다 — 그것은 호출자(표준 `log`)의 것이다.
(SRP: "로그를 어디에 쓰는가" 하나만 소유한다.)

### 2.2 배선: `cmd/rinexclient/main.go` 에서만

```go
w, err := logging.NewRotatingWriter(cfg.LogDir, cfg.LogRetentionDays)
if err != nil { /* §4 강등 정책 */ }
log.SetOutput(io.MultiWriter(os.Stderr, w))
```

- `put.Runner.Logger` 는 계속 nil → `log.Default()` 경유로 자동 수렴.
- `ledger/db.go` 의 직접 호출 1건도 `log.Default()` 이므로 수정 불요.
- **internal 패키지는 `internal/logging` 을 import 하지 않는다.**
  logging 을 아는 곳은 main 하나다. ledger·put 이 logging 에 의존하면
  계층이 역전된다 (domain 최하단 원칙과 동일 계열의 규칙).

### 2.3 config: `[GENERAL]` 키 2개

| 키 | 기본값 | 비고 |
|---|---|---|
| `LogDir` | 실행파일 기준 `logs` | 상대경로는 실행파일 위치 기준으로 해석 (작업 스케줄러의 작업 디렉터리 불확실성 방어 — DPAPI 배포에서 확인된 함정과 동일 계열) |
| `LogRetentionDays` | `30` | 1 미만이면 validate 거부 (설계안 14: 기본 30일) |

`knownKeys` 갱신 + validate 추가. 키가 없으면 기본값으로 동작한다 —
**기존 현장 config.ini 를 수정하지 않아도 로그가 생기기 시작해야 한다**
(10월 최종판 배포 시 config 차분을 최소화).

## 3. 세부 결정과 기각 이유

### 3.1 표준 `log` 유지, `log/slog` 도입 보류 `[기각 이유 기록]`

인시던트 §7-1 은 `log/slog` 를 언급했으나 본 유닛에서는 도입하지 않는다.

- 현재 호출부 전부가 printf 스타일이고 구조화 로그의 소비자(수집기, 파서)가
  없다. 지금 slog 로 바꾸면 30여 호출부를 장애 대응 중에 일괄 수정하는
  위험만 지고 얻는 것이 없다.
- `RotatingWriter` 는 `io.Writer` 이므로 훗날 slog 핸들러 뒤에 그대로
  재사용된다. 도입 시점이 와도 이 유닛의 산출물은 버려지지 않는다.
- 재론 조건: 로그를 기계가 소비해야 하는 요구(모니터링 연동 등)가 생기면
  그때 slog 전환 유닛을 별도로 연다.

### 3.2 파일명·타임스탬프는 로컬 시간 `[기각: UTC]`

로그의 1차 소비자는 현장 운영자다. Windows 작업 스케줄러 이력, 이벤트
뷰어, 탐색기 mtime 이 전부 로컬 시간이므로 대조 단위를 맞춘다.
RINEX 데이터 자체의 UTC(DOY 등)는 로그 **본문**이 파일명·경로로 이미
담고 있어 정보 손실이 없다. 타임스탬프 플래그는 `log.LstdFlags` 유지.

### 3.3 보존 삭제 기준은 파일명 날짜, mtime 아님 `[기각: mtime 기준]`

이번 인시던트의 교훈을 그대로 적용한다 — **mtime 은 신뢰할 수 없는 외부
메타데이터다.** 백업 복원·복사로 mtime 이 갱신된 옛 로그가 영구 생존하거나,
반대로 조기 삭제되는 경로를 차단한다. `rinexclient_YYYYMMDD.log` 패턴에서
파싱되는 날짜만 판단 근거로 쓰고, 패턴 불일치 파일은 **삭제하지 않는다**
(남의 파일을 지우지 않는다 — 삭제는 자기 산출물에만).

### 3.4 flush 요건은 "버퍼를 두지 않음"으로 충족

`os.File` 직접 Write 는 사용자 공간 버퍼가 없다. `bufio` 를 쓰지 않는
것이 곧 라인 보존이다. fsync 를 매 줄 호출하는 것은 `[기각]` — 시간당
수백~수천 줄에서 불필요한 디스크 동기화이며, OS 페이지 캐시 유실은
전원 단절급 사고에서만 발생하고 그 경우 로그보다 큰 문제가 이미 있다.

### 3.5 자정 전환은 Write 시점 판정 `[기각: 타이머 고루틴]`

`Write` 호출 시 현재 로컬 날짜와 열린 파일의 날짜를 비교해 다르면 전환한다.
배경 타이머 고루틴은 두지 않는다 — 이 프로그램은 스케줄러가 매시 기동하는
단명 프로세스라 자정을 걸치는 실행이 드물고, 고루틴은 종료 동기화 부담만
더한다. 판정 비용은 정수 비교 1회다.

### 3.6 파일 열기 실패 시 강등 계속, 중단 아님 `[긴장 기록]`

디스크 만석·권한 오류로 파일을 못 열면 stderr 에 `[LOG][WARN]` 을 남기고
**stderr 단독으로 계속 실행한다.**

- 긴장: "로그 미보존이 추적 불능의 원인이었는데 로그 없이 돌게 두는가?"
- 판단: 로깅은 관측 수단이지 전송의 선결 조건이 아니다. 로그 실패로 전송을
  멈추면 관측 장애가 데이터 장애로 승격된다. 단, 조용히 강등되지 않도록
  경고는 매 실행 남기고, 종료 코드에는 영향을 주지 않는다.
- 회전 중 새 파일 열기 실패도 동일 — 직전 파일에 계속 쓴다(강등 유지).

### 3.7 stderr 병행은 무조건 `[기각: 파일 단독 모드]`

콘솔 억제 옵션은 두지 않는다. 스케줄러 실행에서 stderr 는 버려질 뿐
비용이 없고, 수동 실행·`2>&1` 캡처 관행(인시던트 §9)과의 연속성이 크다.
옵션 하나를 줄이는 것이 config 검증 표면을 줄인다.

## 4. 테스트 계획

| # | 계약 | 방법 |
|---|---|---|
| T1 | 첫 Write 로 디렉터리·파일 생성 | 임시 dir, 파일 존재·내용 검증 |
| T2 | 날짜 전환 | now 주입(테스트 훅) 후 두 날짜 Write → 파일 2개 |
| T3 | 보존 삭제 — 파일명 기준 | 31일 전 이름의 파일 + mtime 오늘 → 삭제됨 / 패턴 불일치 파일 → 생존 |
| T4 | 동시 Write 직렬화 | 고루틴 N개 병렬 기록, `-race`, 줄 수·무결성 검증 |
| T5 | 열기 실패 강등 | 쓰기 불가 dir → error 반환, main 강등 경로는 통합 확인 |
| T6 | 기존 로그와의 배선 | `log.SetOutput` 후 `put` 경유 출력이 파일에 도달 |

now 주입: `NewRotatingWriter` 내부 `nowFn func() time.Time` 비공개 필드
(기본 `time.Now`). 테스트만 교체한다 — put 의 `r.now()` 관행과 동일.

## 5. 커밋 계획 (논리 단위 2개)

1. `logging: RotatingWriter — 일자별 파일·보존 삭제·동시 기록` (+테스트)
2. `main: 파일 로깅 배선 — MultiWriter(stderr, logs\) + config 키 2종`

## 6. 이 유닛이 하지 않는 것 (재론 방지)

- 로그 수준(level) 체계 도입 — 현행 `[SCAN]`/`[PUT]`/`[WARN]` 태그 관행 유지
- 호출부 메시지 문구 변경 — 순서 4(경보)에서 필요분만
- 로그 파일 압축·아카이브 — 요구 없음, 30일 × 일 수 MB 는 부담 아님
- slog 전환 (§3.1)
