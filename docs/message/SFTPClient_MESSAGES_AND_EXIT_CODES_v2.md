# SFTPClient — 메시지와 종료 코드 정리

> 작성: 2026-09-22.
> 목적: 운영자가 보는 안내·경고·오류의 발생 조건, 문구, 종료 코드를 함께 관리한다.
> 기준: [resend 설계 v4](resend/SFTPClient_RESEND_DESIGN_v4.md),
> [SITE 설계 v1](site/SFTPClient_SITE_DESIGN_v1.md), 사용자와의 후속 결정.
> 이번 작업은 문서 작성뿐이다. 아래 정책과 현재 구현의 차이를 자동으로 수정하지 않는다.
> 현재 구현은 작성 시점 작업 트리 기준이며, 미커밋된 커밋 7·8 작업도 포함한다.

## 1. 표기와 적용 범위

- **[확정]**: 사용자가 선택한 정책. 구현 완료를 의미하지 않는다.
- **[현재 구현]**: 실제 코드를 읽어 확인한 동작. 권장 정책과 다를 수 있다.
- **[제안]**: 아직 사용자 결정이 필요한 정책·문구.
- **[미결]**: 처리 우선순위나 적용 범위를 추가로 정해야 하는 항목.

이 문서는 운영 상황별 메시지 모음이다. 모든 내부 `fmt.Errorf` 문자열의
일대일 목록이나 새 오류 번호 체계를 만들지는 않는다. 아래 MSG 식별자는
문서 참조용이며 현재 로그에 구현된 코드가 아니다.

메시지의 조건과 종료 정책을 먼저 정하고, 실제 문자열 변경은 해당 구현 커밋에서
수행한다. 기존 로그 태그·카운터를 한꺼번에 바꾸지 않는다. 보안 자격증명은
메시지에 출력하지 않는다.

## 2. 종료 코드의 뜻

### 2.1 코드 0 — 정상 종료

0은 파일을 반드시 전송했다는 뜻이 아니다. 정상적인 조건으로 탐색·처리가
끝나거나, 정해진 정책대로 실행을 생략한 경우도 포함한다.

예: 이미 VERIFIED, 정상 탐색 결과 자료 없음, 정상 dry-run, 정시 lock 양보,
파일 수 예산 소진에 따른 자동 resend 생략.

또한 **현재 구현에서는 파일별 실패나 디렉터리 나열 오류가 있어도 0으로
끝날 수 있다.** 따라서 현재 운영에서 0만 보고 모든 파일의 성공을 단정하지 않는다.

### 2.2 코드 1 — 오류 반환에 따른 비정상 종료

현재 `main()`은 `run()`이 오류를 반환하면 `[FATAL]`을 기록하고 `os.Exit(1)`을
호출한다. 설정·입력 오류, 연결 실패, DB 오류, 전파된 취소·stall 등이 해당한다.

1이라고 모든 파일이 실패했거나 성공 파일이 롤백됐다는 뜻은 아니다.
일부 성공 후 중단되면 VERIFIED 기록은 유지되고, 다음 실행이 기존 Ledger
규칙에 따라 남은 대상을 선택한다. 종료 코드만으로 원인을 구분하지 않으며
로그의 구체적인 사유를 함께 확인한다.

### 2.3 0·1만 존재한다고 가정하지 않는다

**[현재 구현]** 일반 정시 진입점은 Go 기본 `flag.CommandLine`을 사용하므로
플래그 파싱 오류가 코드 2로 프로세스를 종료할 수 있다. 수동 resend는
`flag.ContinueOnError`로 파싱 오류를 반환하므로 main을 통해 1이 된다.
현재 수동 `resend --help`도 `flag.ErrHelp`를 그대로 반환해 1로 끝날 수 있다.

- **[제안]** 도움말 요청은 정상 안내이므로 0으로 처리한다. 이때
  `flag.ErrHelp`는 main의 `[FATAL]` 기록도 억제한다 — 도움말을 본
  사람에게 FATAL 이 찍히면 그것대로 오해를 만든다.
- **[미결]** 일반 실행과 서브커맨드의 입력 오류 종료 코드를 1로 통일할지.
- 외부 강제 종료·OS 신호에 의한 종료는 애플리케이션의 0/1 계약과 별개다.
  Linux SIGTERM 처리는 경로 범용화 이후 Linux 배포 작업에서 정리한다.

### 2.4 로그 수준과 종료 코드는 별개다

WARN은 계속 처리해도 되는 상황에도 쓰인다. WARN이 있다고 반드시 1은 아니고,
INFO 요약에 `failed=`나 `errs=`가 기록된다고 자동으로 1이 되는 것도 아니다.
내부 sentinel error, 로그 태그, 프로세스 종료 코드를 혼동하지 않는다.

## 3. 현재까지 합의한 정책

1. 수동 resend의 lock 재시도 간격은 **10초 [확정]**.
2. lock 대기 중 반복 안내는 **5분 간격 [확정]**.
   첫 대기 안내는 즉시 한 번이고, 획득·시간 초과·취소 안내는 별개다.
   현재 코드는 `lockWaitLogEvery = 5 * time.Minute`이다.
3. 전체 lock 대기 상한은 설정 `LockStaleSeconds`다. 재시도마다 초기화하지 않는다.
4. 정상 탐색의 일반적인 선택 0건은 **exit 0 + 사유 표시 [확정]**.
5. 지정 site 자료가 없을 때 안내는
   **"입력한 관측소({sites})의 파일이 해당 기간에 없습니다. 관측소 코드를 확인하세요." [확정: 문구]**.
   `{sites}`는 운영자가 입력한 값의 대문자 표기다(예: `DBOM`). 예시 관측소를
   문구에 박제하지 않는다 — 복수 site 표기(§6-3 미결)가 정해지면 이 자리에 들어간다.
6. 위 site 자료 미발견 상황은 **exit 1 [확정]**. 관측소 오타가 증명됐다는 뜻은 아니다.
   이 항목은 4번 일반 원칙에 대한 **명시적 예외**다 — "site를 지정했다"는 사실이
   운영자의 기대를 담고 있으므로, 그 기대가 비었음을 코드로 알린다.
7. 기간에 자료가 없을 때 문구는 **"해당 기간에 데이터가 없습니다." [확정]**.
8. Linux 관련 정책·경로 정리는 경로 범용화 이후 별도 수행한다 **[확정]**.

4번의 일반 원칙과 6번의 site 예외가 겹칠 때의 우선순위는 §6에서 미결로 관리한다.
**6번 예외는 §6의 미결 3건(1·2·3항)을 닫기 전에는 구현할 수 없다** — 겹침 규칙
없이 예외만 구현하면 같은 0건이 실행마다 다른 코드로 끝난다. §6 결정 시 예외의
운영 비용도 함께 본다: "혹시 누락 있나" 확인차 돌린 정상 조회가 exit 1로 끝나는
경우가 생기며, 그것이 감수할 만한지가 판단 대상이다.

## 4. 메시지 목록 — 입력·설정

### MSG-INPUT-01 필수 인자 누락·형식 오류

- 조건: `--from`/`--to` 누락, 잘못된 날짜, site가 4자리 영숫자가 아님,
  빈 목록 요소, 알 수 없거나 비활성인 category, 지원하지 않는 플래그 등.
- 문구 **[제안]**: “입력한 {인자} 값이 올바르지 않습니다: {값}. {허용 형식}을 확인하세요.”
- 처리: 실행 전에 거부. 문법 오류를 site 전체 선택으로 확대하지 않는다.
- 종료: 수동 resend는 현재 1. 일반 실행의 플래그 파싱 오류는 §2.3 참조.
- **[현재 구현]** `--site`·`--category` 생략은 전체 선택이다. 명시적 빈 값
  (`--site=""`, `--category=""`, 공백만)은 `flag.Visit`로 지정 여부를 구분해
  실행 전에 거부한다. 빈 값을 전체 선택으로 확대하지 않는다.
- **[현재 구현]** `resend`와 `secure-set`은 첫 인자일 때만 서브커맨드다.
  정기 실행에 위치 인자가 남으면 전송을 시작하지 않고 거부한다.
  `rinexclient --config x resend ...`는 live 전송이 되지 않는다.
  수동 재전송은 `rinexclient resend ...`만 쓴다.

### MSG-INPUT-02 허용 기간 위반

- 조건: From > To, To가 UTC 오늘보다 미래, From이 Retention 한계보다 과거.
- 문구 **[제안]**: “요청 기간이 허용 범위를 벗어났습니다. 요청={from}~{to}, 허용={limit}~{today} (UTC).”
- 처리·종료: 요청 거부, 1. Retention 밖을 강제로 여는 옵션은 없다.
- 기준: v4의 `limit = UTC today − (RetentionDays − 2)`를 그대로 따른다.
  수동 요청에는 운영 시작일(origin) 하한을 적용하지 않는다.

### MSG-CONFIG-01 설정·운영 시작일 오류

- 조건: 설정 필수 키 누락·오타·유효성 위반, 운영 시작일 손상, Ledger 오류 등.
- 문구 **[현재 구현]**: 원인별 반환 오류를 main의 `[FATAL]`이 기록한다.
- 처리·종료: 중단, 1. 잘못된 origin을 오늘이나 Retention 한계로 대체하지 않는다.
- 주의: `MaxFilesPerRun=0`은 현재 무제한이다. 이를 거부하는 Q14는 미결이며
  이 메시지 정리를 근거로 정책을 바꾸지 않는다.

## 5. 메시지 목록 — 탐색과 선택 0건

### 5.1 집계 해석

- `dirs`: 디렉터리 나열 성공.
- `missing`: `fs.ErrNotExist`로 분류된 디렉터리 부재.
- `Scan.Files`(scanned): 성공적으로 나열한 항목 수. 하위 디렉터리도 포함하므로
  유효한 파일 수나 관측소 자료 수가 아니다. `scanned > 0`만으로 다른 관측소
  자료가 있다고 판단하지 않고, 파일명에서 site를 식별한 결과를 사용한다.
- `errs`: 그 외 디렉터리 나열 오류. 일부 경로를 확인하지 못한 상태.
- `Failures`: 나열 실패의 경로·원인 표본. 현재 최대 10건이므로 전체 목록이라고 표시하지 않는다.
- `site_mismatch`: 식별한 site가 선택 조건에 맞지 않아 제외.
- `site_unknown`: site를 식별할 수 없어 제외.
- `kept`: 게이트·재시도·예산·세트 경계 조정을 거친 이번 실행 후보.

`kept=0`만으로 데이터 부재를 판단하지 않는다. 탐색 오류, site 선택,
VERIFIED, 보류, 예산 절단은 서로 다른 원인이다. 여러 카테고리·시간 슬롯을
탐색하므로 `missing`을 단순히 요청 날짜 수와 비교하지 않는다.

### MSG-SCAN-01 해당 기간에 데이터 없음

- 조건: 탐색 오류가 없고, 대상 디렉터리가 모두 없거나 성공적으로 연 폴더가 비어
  대상 파일을 발견하지 못한 경우. site 필터로 0건이 된 상황과 구분한다.
- 문구 **[확정]**: “해당 기간에 데이터가 없습니다.”
- 보조 정보 **[제안]**: 이 줄에 요청 기간·카테고리·LocalPath를 반복하는 것은 아직이다.
  dirs/missing은 이미 같은 줄에 있다.
- **[현재 구현]** site를 지정하지 않았고, 탐색 오류가 0이며, 나열 엔트리가 0일 때만
  확정 문구를 쓰고 exit 0이다. 그 중 디렉터리가 하나도 안 열리고 `missing`만
  있으면(`[dirs=0 missing>0]`) 확정 문구 뒤에 경로·드라이브·마운트 확인 WARN을
  붙인다. 저장소가 정상이라고 단정하지 않는다. site 지정, 엔트리 있음,
  `errs>0`은 이 문구를 쓰지 않는다.

### MSG-SITE-01 지정 관측소 자료 미발견

- 조건: 형식은 유효한 site를 지정했지만 그 관측소의 파일을 해당 기간에서
  발견하지 못했다. 구체적인 판정 모집단과 다른 0건 사유와의 우선순위는 §6 미결.
- 문구 **[확정: 템플릿]**: “입력한 관측소({sites})의 파일이 해당 기간에 없습니다. 관측소 코드를 확인하세요.”
- 종료 **[확정]**: 1. 요청 조건 확인을 요구하는 운영 정책이며, 문법 오류와는 다르다.
- 금지: “관측소가 틀렸습니다”라고 단정하지 않는다. 관측소 등록부가 없어서
  코드 오타와 해당 기간의 관측소 자료 부재를 구분할 수 없다.
- **선행 계약**: “발견”은 kept가 아니라 **요청 site와 일치하는 파일의 관측**으로
  판정한다. 전부 VERIFIED여도 발견된 것이며, 안정성 검사·세트 조건으로 보류된
  파일도 미발견과 구분한다. 관측은 해당 검사·후보 제외 전에 기록해야 한다.
  임시 입력·식별 불가 이름의 처리는 §6-4에서 별도로 정한다.
  `site_mismatch`/`site_unknown`만으로는 이 판정이 되지 않는다. 요청 site별
  일치 관측이 필요하고, 합계만으로는 `DBON,DBOM` 중 DBON만 발견된 상황을
  구분할 수 없다.
- **[현재 구현]** 요청 site별 일치 관측은 `SiteMatched`로 후보 제외 전에 세고,
  0건 로그에 `site_matched=DBON:0`처럼 남긴다. 합계로 대신하지 않는다.
  exit 1 예외는 §6 미결을 닫기 전에는 구현하지 않으므로, 이 경우도 exit 0이다.
  확정 문구(“입력한 관측소…”)는 아직 이 로그에 쓰지 않는다.
- 여러 site 중 일부만 없는 경우: 종료 정책은 §6 미결. 발견 수 자체는 site별로 남긴다.

### MSG-SELECT-01 이미 전송 완료

- 조건: 선택 조건에 해당하는 파일은 있으나 현재 revision이 모두 VERIFIED여서 후보가 없음.
- 문구 **[제안]**: “선택한 자료는 이미 전송 완료되어 보낼 파일이 없습니다.”
- 종료: 정상적인 후보 0건이므로 0.
- 주의: site 파일의 발견 수를 최종 kept 수로 세면 완료 파일을 미발견으로 오판한다.

### MSG-SELECT-02 조건 미충족으로 보류·제외

- 조건: 세트 최소 종 미충족, 미완성 입력·안정성 검사, origin 정책 등으로 후보가 없음.
- 문구 **[제안]**: “대상 자료가 있지만 전송 조건을 충족하지 않아 보류·제외했습니다: {사유별 건수}.”
- 종료: 정상 판정으로 후보가 없는 경우 0. 별도 I/O·DB·탐색 오류가 있으면 그 오류 정책을 적용.
- 금지: 보류를 ‘전송 완료’나 ‘해당 기간 데이터 없음’으로 표시하지 않는다.

### MSG-SCAN-02 탐색 불완전

- 조건: 어느 카테고리에서든 `Scan.Errs > 0`. 최종 후보 0건과 일부 후보 존재 모두 해당.
- 문구 **[제안]**: “일부 경로를 읽지 못해 요청 범위 전체를 확인하지 못했습니다. 탐색 오류={errs}. {실패 경로·원인 표본}.”
- 현재 구현: Scanner는 Errs/Failures를 기록하고 다른 경로를 계속 탐색한다.
  별도 fatal 오류가 없다면 정시·수동 모두 0으로 끝날 수 있다.
  수동이고 후보가 0이며 `errs>0`이면 그 로그에 “정상 종료”라고 쓰지 않는다.
  종료 코드는 아래 미결 그대로 0이다. 후보가 있으면 전송을 계속한다.
- **미결**: 수동 명령의 종료 코드. 전달된 다른 AI 제안은 WARN+0,
  이번 대화의 제안은 요청 범위가 불완전하므로 1. 아직 사용자가 최종 선택하지 않았다.
- **미결**: 읽을 수 있었던 파일은 전송한 뒤 1로 끝낼지, 전송 전에 요청을 중단할지.
  정시 정책을 함께 변경하는 것으로 해석하지 않는다.

## 6. 겹치는 조건의 우선순위 — 구현 전 확정 필요

1. **탐색 오류와 site 미발견이 겹침:** 읽지 못한 폴더에 해당 site가 있을 수 있다.
   먼저 탐색 불완전을 표시하고 site 오타로 유도하지 않는 것을 제안한다.
2. **기간 전체 데이터 없음 + site 지정:** 전체 데이터 없음은 0, 다른 관측소
   자료는 있는데 지정 site만 없으면 1로 구분하는 것을 제안한다. 아직 확정 아님.
3. **복수 site 중 일부 미발견:** 발견된 site만 전송할지, 실행을 전부 거부할지,
   일부 전송 후 1로 끝낼지 미결이다. site별 알림 추가도 합의 없이 구현 범위로 확정하지 않는다.
4. **파일은 있으나 모두 임시·식별 불가:** 데이터가 없거나 site가 틀렸다고 단정하지
   않고 제외 사유를 표시한다. site ‘발견’의 정확한 집계 시점은 후속 구현에서 고정한다.
5. **전송 완료·보류·제외가 혼재:** 단일 원인을 임의로 선택하지 않고 사유별 건수를 표시한다.

## 7. 메시지 목록 — lock과 실행 제어

### MSG-LOCK-01 다른 실행이 lock 보유

- 정시 실행 **[현재 구현]**: `[LOCK] ... — exiting`, 이번 회차 생략, exit 0.
- 수동 resend **[확정]**: 즉시 첫 획득 시도 후 ErrHeld일 때만 10초 간격 재시도.
- 대기 문구 **[제안]**: “다른 실행이 작업 중입니다. lock 해제를 기다립니다. 재시도=10초, 대기 상한={값}.”
- 반복 로그 **[현재 구현]**: 5분(`lockWaitLogEvery = 5 * time.Minute`).
  첫 `ErrHeld`에서는 즉시 한 번 알리고, 그 다음부터 5분마다 반복한다.
- 권한 오류 등 ErrHeld 이외의 오류는 대기하지 않고 1로 종료한다.
- 대기 중 Ctrl+C는 재시도 간격 종료까지 기다리지 않고 취소해야 한다.

### MSG-LOCK-02 대기 상한 초과

- 조건: 수동 명령의 전체 대기가 설정 LockStaleSeconds에 도달.
- 문구 **[제안]**: “lock 대기 시간이 상한을 초과했습니다. 실행 중인 작업을 확인한 뒤 다시 실행하세요.”
- 처리·종료: 대기를 끝내고 1. lock 강제 삭제를 일반 해결 안내로 제시하지 않는다.
- 대기 상한과 기존 owner의 stale 나이 판정은 별개다. 수동·정시 모두 같은
  설정 stale 기준을 사용하며 수동만 24시간 보호한다는 규칙은 폐기됐다.
- 상한 시각을 한 재시도 간격(10초) 남짓 넘긴 뒤의 `Acquire`가 이미 stale인
  락을 가져갈 수 있다. 상한을 재시도마다 늘리지는 않는다.

### 수동 resend가 정시 회차와 겹칠 때 [현재 구현]

- dry-run을 포함해 수동 명령은 스캔과 전송이 끝날 때까지 정시와 같은 락을 잡는다.
  락은 접속보다 먼저 잡는다. 대기 중에는 SFTP 세션을 열어 두지 않는다.
- 해시와 장부 반영은 `MaxFilesPerRun` 절단보다 먼저다. 관측소·카테고리를 비우고
  보존 기간 전체를 주면, 이번 실행 건수가 적어도 락을 오래 잡을 수 있다.
  그 사이 정시는 `ErrHeld`로 빠지고 exit 0이다.
- 대기 중인 수동 명령은 10초마다 `Acquire`한다. 상대 락의 나이가
  `LockStaleSeconds`를 넘는 순간, 다음 정시까지 기다리지 않고 10초 안에 가져간다.
  상대가 아직 돌고 있으면 양쪽이 동시에 전송한다. 가져간 쪽의 `Recover`는
  남은 `IN_PROGRESS`를 `FAILED`로 되돌리고 원격 `.part`를 지운다.
- `Recover`는 site로 좁히지 않는다. 한 관측소만 재전송해도, 남아 있던
  다른 관측소의 `IN_PROGRESS`를 함께 회수한다.
- 파일별 전송 실패만 있으면 수동도 exit 0일 수 있다. 파일을 보냈는지는
  로그의 `failed=`로 본다. 이 종료 코드를 1로 바꿀지는 MSG-XFER-01에서 미결이다.
- 운영 시작일 이전은 `before_origin=`만 남기고 거절하지 않는다. 장부에 없는
  파일은 신규로 전송되므로, 예전 수단이 이미 보낸 파일이면 원격에 다시 쓴다.

### MSG-AUTO-01 자동 resend 생략

- 조건: 남은 예산 없음, origin 이전이라 빈 창, Retention 설정상 빈 창 등.
- 문구 **[현재 구현]**: `[RESEND] skipped (...)`, 설정상 빈 창은 WARN.
- 종료: 별도 오류가 없으면 0. 첫 운영 시 before_origin은 정상적인 보호 동작이다.
- stall·fatal PUT 오류로 중단된 회차는 1이며, 정상 생략과 구분한다.

### MSG-BUDGET-01 파일 수 상한 도달

- 조건: MaxFilesPerRun 및 세트 경계 조정으로 후보 일부가 이번 실행에서 제외.
- 문구 **[제안]**: “이번 실행의 파일 수 상한에 도달했습니다. 선택={kept}, 이번 실행 제외={cut}.”
- 종료: 선택된 작업이 정상 처리됐다면 상한 도달 자체는 오류가 아니므로 0.
- 자동 창 밖이거나 소진된 수동 재시도 대상은 다음 자동 실행이 반드시 이어받는
  것이 아니다. 모든 잔여 파일에 ‘다음 정시에 자동 전송’이라고 약속하지 않는다.

## 8. 메시지 목록 — 전송·취소·로그

### MSG-XFER-01 파일별 전송 실패

- 조건: 파일 업로드·원격 경로 준비 등의 실패를 FAILED로 기록한 경우.
- 현재 구현: Transfer의 반환 오류가 nil이어도 `TransferReport.Failed > 0`일 수 있다.
  현재 정시 PUT·자동 resend·수동 resend 호출부는 이 집계만으로 오류를 반환하지 않는다.
  따라서 파일별 실패만 있으면 종료 코드는 0이다.
- **[확정·구현 완료 2026-09-22] ②(자동 resend) 차단 조건** — ①이 파일 단위로
  **한 건도 성공하지 못하면**(`failed > 0 && verified == 0`) ② 를
  `[RESEND][WARN] skipped (put error: failed=N verified=0)` 로 건너뛴다.
  종료 코드는 0 그대로다(파일 단위 실패는 retry 체계의 몫). **일부라도
  성공했으면 ② 는 진행한다** — 개별 파일의 국지 실패로 그 회차의 누락
  복구 전체를 멈추지 않는다. 근거: 전실패는 원격 장애 신호라 ② 가 같은
  원인으로 attempts 만 태울 가능성이 크고, 부분 실패는 그렇지 않다.
  운영 테스트 `put_failure_blocks_resend`(전실패→차단)와
  `resend_failure_keeps_exit_0`(②의 파일 실패도 exit 0)이 이 계약을 고정한다.
- **정책 미결**: 이전 설명에서는 실패 시 1을 제안·일시 반영했지만 현재 작업 트리는
  그 처리를 유지하지 않는다. ‘파일별 실패는 1로 구현 완료’라고 기록하지 않는다.
- **[제안: 2026-09-22 Claude 검토]** 세 갈래로 나눈다 — ① **정시는 0 유지**:
  기존 정시 종료 정책과 재시도 체계를 유지하는 안이다. 이 경우 파일별 실패
  감시는 종료 코드가 아니라 로그·실패 집계·소진 WARN에 의존한다.
  실패마다 1을 반환하는 정책의 적합성은 스케줄러·모니터링 운영 방식에 따라
  달라지므로, 반복적인 1이 반드시 신호를 무의미하게 만든다고 단정하지 않는다.
  ② **수동은 failed>0 이면 1**: 사람이 결과를 기다리는 명령이므로 실패를
  코드로 알린다. — 이 두 갈래(정시·수동의 종료 코드)는 여전히 사용자
  미확정이다. (원안의 ③ "② 를 차단하지 않는다"는 위 확정으로 대체되었다 —
  전실패만 차단하는 절충이 채택되어 원안의 우려였던 "국지 실패로 복구
  전체가 멈춤"은 부분 성공 시 진행으로 해소됐다.)
- 제안 문구: “일부 파일 전송에 실패했습니다. 성공={verified}, 실패={failed}. 실패 내역을 확인하세요.”
- 선택 필요: 파일별 실패도 exit 1로 할지, 기존 집계+exit 0을 유지할지
  (정시·수동 각각). ② 차단 여부는 위 확정으로 닫혔다.
- 이미 VERIFIED인 성공 파일은 유지한다. 실패로 revision을 올리거나 attempts를 초기화하지 않는다.

### MSG-XFER-02 회차 중단 오류·stall

- 조건: 연결 실패, Ledger 상태 기록 실패 등 fatal 오류, SFTP 무진행 감시 발화.
- 현재 구현: 오류를 상위로 반환해 `[FATAL]`과 exit 1. stall은 `[STALL]` 경고도 남긴다.
- 안내 **[제안]**: “전송 회차가 중단되었습니다: {원인}. 이미 완료된 파일은 유지됩니다.”
- 기존 취소·SSH Abort·상태 기록·lock 해제 경로를 유지한다. 새 시간 가드를 추가하지 않는다.

### MSG-CANCEL-01 사용자 취소

- 조건: Ctrl+C로 context가 취소되고 오류가 상위로 전파됨.
- 현재 구현: main을 통한 종료는 1. 외부 강제 종료와 동일한 코드라고 보장하지 않는다.
- 문구 **[제안]**: “사용자 요청으로 작업을 취소했습니다. 완료된 전송은 유지됩니다.”
- Linux SIGTERM 연결은 경로 범용화 이후 검토한다.

### MSG-LOG-01 로그 저장 실패

- 현재 구현: 파일 로그 초기화·쓰기 실패는 WARN 후 전송 계속. 로그 실패만으로
  전송을 중단하거나 exit 1로 바꾸지 않는다. stderr 출력과 실제 전송 결과를 구분한다.

### MSG-INFO-01 dry-run·수동 origin 이전 요청

- dry-run: 전송 없이 후보·사유를 관측한다. 정상 관측은 0이며 입력·탐색 오류 정책은 별도다.
- 수동 origin 이전 기간: Retention 안이면 허용하고 `before_origin=` 정보를 남긴다.
  origin 이전이라는 이유만으로 실패 처리하지 않는다.

## 9. Windows·Linux 공통 주의사항

- Windows 경로·드라이브 부재가 missing으로 나타날 수 있다.
- Linux에서도 마운트 해제 후 하위 경로가 없어지거나, 마운트 지점 아래의 빈
  로컬 디렉터리가 보여 missing 또는 나열 성공·0건으로 나타날 수 있다.
  NFS 장애가 언제나 missing인 것은 아니며 I/O 오류나 대기로 나타날 수도 있다.
- 파일 목록만으로 ‘실제 자료 없음’과 ‘저장소 연결 이상’을 항상 구분할 수 없다.
  경로 표시는 진단 보조이며 마운트 정상 여부를 검증한 결과가 아니다.
- Linux 파일 경로의 대소문자와 site 코드 정규화는 별개다. site 매칭이
  대소문자를 무시하더라도 실제 경로를 임의로 소문자로 바꾸지 않는다.
- ‘정상 탐색’은 프로그램이 받은 결과를 정상으로 분류했다는 뜻이며,
  원본 저장소가 실제 연결돼 있었다는 절대적인 보장은 아니다.
- OS별 종료 신호·테스트 경로 정리는 경로 범용화 이후 Linux 작업으로 남긴다.

## 10. 현재 구현과 결정 사이의 차이

1. lock 재시도 10초와 반복 로그 5분은 구현됨.
2. site 자료 미발견의 확정 문구와 exit 1은 §6을 닫기 전에는 미구현이다.
   0건 로그의 `site_matched=`와 exit 0은 구현됨.
3. 기간 자료 없음은 site 미지정·탐색 오류 0·엔트리 0일 때 확정 문구를 쓴다.
   이미 완료·보류를 그 문구와 구분하는 한국어 안내는 아직 일반 집계다.
   디렉터리가 모두 없을 때의 마운트 WARN은 구현됨.
4. 탐색 불완전의 수동 종료 코드와 일부 전송 여부는 미결. 후보 0건일 때
   “정상 종료”라는 문구는 쓰지 않는다.
5. 파일별 전송 실패의 **종료 코드**(정시·수동)는 미결. **② 진행 정책은
   확정·구현됨** — 전실패(`verified=0`)만 차단, 부분 성공은 진행, exit 0 유지.
6. 명시적 빈 site·category, 플래그 뒤에 붙은 `resend`가 정기 전송으로 새는
   경로는 막았다. 도움말 요청의 exit 0과 일반 실행의 exit 2 통일은 미결.
7. 복수 site 중 일부만 미발견인 경우의 종료·전송 정책은 아직 미결.
   요청 site별 발견 수는 남긴다.
8. 이 문서의 [확정] 중 락 간격·정상 선택 0건 exit 0은 v4 §6.3과 SITE §7-5에
   반영했다. site 미발견 exit 1은 메시지 문서 §6을 닫은 뒤 구현한다.

## 11. 후속 구현 검증 기준

- 동일한 0건이라도 자료 없음 / site 미발견 / 이미 VERIFIED / 보류가 구분되는가.
- dirs=0, missing>0, errs=0을 자료 부재로 안내하되 저장소 정상이라고 단정하지 않는가.
- errs>0을 정상 탐색 0건으로 표시하지 않는가. 일부 선택이 있어도 오류가 드러나는가.
- 복수 site 미발견을 최종 kept 수나 합산 관측 수로 오판하지 않는가.
  site별 안내를 채택하면 요청 site별 발견 정보를 사용하는가.
- site가 일치하지만 이미 VERIFIED이거나 안정성·세트 검사로 보류된 파일을
  미발견으로 오판하지 않는가.
- 도움말 정상 종료 정책을 채택하면, 요청이 0으로 끝나고 `[FATAL]` 없이
  사용법만 출력되는가.
- lock은 10초마다 확인하고 반복 로그는 5분마다 나오며 취소에 즉시 반응하는가.
- 대기 상한이 재시도 때마다 갱신되지 않는가.
- 정시·수동·dry-run의 종료 코드 차이가 문서의 확정 정책과 일치하는가.
- 전송 일부 실패와 fatal 오류를 각각 검증하고, 실제 프로세스 종료 코드까지 확인하는가.
- 정상적인 상한 도달을 실패로 오인하거나 전체 요청 완료로 과장하지 않는가.

## 12. 구현 근거

- [main.go](../cmd/rinexclient/main.go): 종료 1 처리, 정시 lock 양보, 자동 resend 배선.
- [resend.go](../cmd/rinexclient/resend.go): 수동 인자·대기·0건 안내·전송 결과 처리.
- [scan.go](../internal/scan/scan.go): dirs/missing/errs와 Failures 수집.
- [runner.go](../internal/put/runner.go): site 제외·게이트·후보 판정.
- [transfer.go](../internal/put/transfer.go): 파일별 실패 집계와 fatal 오류 구분.
- [autoresend_operations_test.go](../cmd/rinexclient/autoresend_operations_test.go): 정시 운영 시나리오의 현재 기대 동작.

현재 구현 설명은 작성 시점의 관찰이다. 후속 커밋에서 동작을 바꾸면 해당 항목의
상태와 테스트를 함께 갱신하고, 제안만으로 기존 정책을 덮어쓰지 않는다.
