## 0. 한 줄 요약

**원격 SFTP의 완성 파일을 읽기만 해서 받아 오고, 관측소(`(SITE)`) 폴더로 나눠 저장한다.
download와 put은 서로 모르는 별개 모듈이다. common은 "다운로드 끝났으니 보내라"를 요청하고 Ping-Pong을 막을 뿐,
데이터를 판단하지 않는다. put은 기존 로직 그대로이며, 받은 파일을 로컬 파일로 인식해 보낸다.
이 프로젝트의 핵심은 결합도를 최대한 낮추는 것이다.**

### 0.1 기본 기조: PUT 전용이 기본이다

- **이 프로그램의 기본 사용 형태는 PUT 전용이다.** 현재 설치처와 앞으로의 설치처 대부분은 PUT만 쓴다.
- **DOWNLOAD와 BOTH는 측위원 외에는 쓰일지 알 수 없다.** 올인원 요구([지시])에 따라 기능은 갖추되,
  측위원 한 곳을 위한 선택 기능으로 취급한다.
- 따라서 이 문서의 모든 결정은 다음 우선순위를 따른다.
  1. **PUT 전용 설치처에 영향이 없을 것.** 설정을 바꾸지 않은 PUT 현장은 새 버전을 받아도 동작·로그·설정·DB가 그대로여야 한다.
  2. DOWNLOAD는 켠 곳에서만 동작하고, 켜지 않으면 비용(접속·장부 쓰기·로그)이 0이다.
  3. 측위원에 필요 없는 일반화·최적화는 미룬다. 필요가 확인되면 그때 넓힌다.

## 3. 모듈 구조 [결정 2026-09-24]

```
 ┌────────────┐                 ┌────────────┐                 ┌────────────┐
 │  download  │ ── 끝났음 ─────▶ │   common   │ ── 보내라 ─────▶ │    put     │
 │ 원격 → 로컬 │                 │ 순서 조율   │                 │ 로컬 → 원격 │
 │            │                 │ Ping-Pong  │                 │ (기존 그대로)│
 │            │                 │ 차단        │                 │            │
 └─────┬──────┘                 └────────────┘                 └─────┬──────┘
       │ 파일을 쌓는다                                                  │ 로컬 파일로 인식해 보낸다
       ▼                                                               ▲
   [ 타겟 폴더 (DOWNLOAD LocalPath = PUT LocalPath 아래) ] ─────────────┘
```

| 모듈 | 하는 일 | 하지 않는 일 |
|---|---|---|
| **download** | 원격 나열 → 받을지 판단(자기 수신 기록) → 타겟 폴더에 쌓기 | put을 알지 못한다 |
| **common** | ① download가 끝나면 put에 "보내라"고 요청한다 ② 시작 시 설정을 보고 Ping-Pong 구성을 거부한다 (§3.2) | **데이터를 판단하지 않는다.** 어떤 DB도 읽지 않는다. 파일 목록을 넘기지 않는다 |
| **put** | **기존 로직 그대로.** 타겟 폴더의 파일을 다른 로컬 파일과 똑같이 인식해 보낸다 | download를 알지 못한다. 받은 파일인지 구분하지 않는다 |

### 3.1 common은 조율자이지 판단자가 아니다

- common이 주고받는 것은 "끝났다", "보내라"뿐이다. 이번 회차에 무엇을 받았는지 목록을 put에 넘기지 않는다.
  put은 어차피 자기 스캔으로 폴더를 본다.
- 한 프로세스 안에서 common은 `cmd`의 얇은 조립이다. `download.Run`이 끝나면 `put.Run`을 부른다.
  별도 스레드·큐·타이머를 두지 않는다. **신호 = 함수 호출 순서**다.
- 텀은 두지 않는다. download가 끝나야 요청이 가고, 받은 파일의 mtime이 받은 시각이라 put의 `GraceSeconds`가 자연히 텀이 된다.
- DOWNLOAD만 쓰는 현장(`Mode=download`)에서는 common이 할 일이 없다. PUT만 쓰는 현장(`Mode=put`)도 마찬가지다.
  common은 BOTH에서만 동작한다.

### 3.2 Ping-Pong 차단: 데이터가 아니라 설정으로

put이 받은 파일을 로컬 파일로 보내는 것은 **의도된 동작**이다(측위원 중계: 중계 서버 → 측위원 PC → 지리원).
막아야 하는 것은 **순환**이다. 올려 보낸 파일을 다시 받아 오고, 받은 파일을 또 올려 보내는 고리다.

| 순환 조건 | common의 처리 |
|---|---|
| PUT 목적지 서버 = DOWNLOAD 원본 서버 (**같은 host:port**)이고, PUT RemotePath가 DOWNLOAD RemotePath 스캔 범위와 겹침 | **시작 거부** |

- 판정은 시작 단계에서 **설정 두 줄을 비교**할 뿐이다. 파일이나 DB를 보지 않는다.
- 겹침 판정은 첫 토큰 앞 고정 부분을 비교한다(보수적). 애매하면 거부한다.
- 호스트가 다르면 경로가 같아도 순환이 아니다. 서로 다른 서버다.

### 3.3 결합도를 낮춘 대가 [결정: 감수]

| 잃는 것 | 이유 | 대응 |
|---|---|---|
| put이 "받은 파일"과 "원래 있던 파일"을 구분하지 못한다 | put은 download를 모른다 | 구분이 필요 없는 구성만 지원한다. 타겟 폴더를 PUT LocalPath 아래에 두면 중계, 밖에 두면 수신만 한다. **폴더 배치가 곧 의도**다 |
| 받은 파일이 뜻하지 않게 전송될 수 있다 (타겟 폴더를 실수로 PUT LocalPath 아래에 둔 경우) | 위와 같음 | 운영 절차·설정 예시로 안내한다. 코드로 막지 않는다 |
| 기존의 `origin=DOWNLOAD` 기록과 `RepostDownloaded`가 쓰이지 않는다 | download가 PUT DB에 쓰지 않으므로 모든 파일이 `origin=LOCAL`이다 | PUT 코드는 그대로 둔다(원칙 4). 쓰이지 않는 키·값은 문서에 "미사용"으로 적고 정리는 나중에 한다 |
| 파일 하나의 수신 → 송신 이력을 한 번에 조회할 수 없다 | 수신 기록과 송신 기록이 서로 연결되지 않는다 | 필요하면 운영 조회에서 파일명으로 두 기록을 나란히 보여 준다(읽기 전용). 판단에는 쓰지 않는다 |

## 4. DOWNLOAD 흐름

```
[원격 SFTP]                                           [로컬]
 RemotePath 템플릿 (날짜 전개)
   │ ① scan.Scanner + SFTPLister  (재귀 — (HH) 폴더 포함)
   ▼
 원격 Entry 목록
   │ ② verify.Verifier            (.part/0바이트/Grace/카테고리 불일치 거부)
   │ ③ Sites 필터 · (SITE)/(HH) 값 추출 (실패 → 제외·집계)
   │ ④ 판정 (§6.3): 수신 기록·로컬 파일로 받기 / 건너뜀 / 기존 파일 인정
   │ ⑤ 원격 Open → 로컬 .part 쓰기                            ──▶  LocalPath\(SITE)\...\name.part
   │ ⑥ 크기 검증: 로컬 .part == 원격 size
   │ ⑦ Rename .part → 최종 이름                               ──▶  LocalPath\(SITE)\...\name
   │ ⑧ 수신 기록: 성공 / 실패 + 원인
   ▼
 회차 종료 → common에 완료 신호 (§3)
```

- **결과만 기록한다.** PUT처럼 전송 전에 IN_PROGRESS를 쓰고 시작 시 회수하는 절차를 두지 않는다.
  중간에 끊기면 성공 기록이 없으므로 다음 회차가 다시 받는다. `.part` 이름이 결정적(`최종이름.part`)이라
  재시도가 이전 조각을 덮어쓴다. 원격에서 파일이 사라져 재시도가 없으면 고아 `.part`가 남을 수 있으나,
  PUT Ingress는 `.part`를 거부하므로 무해하다.
- **⑦ 뒤 ⑧ 전에 끊기면** 최종 파일은 있는데 성공 기록이 없다. 다음 회차의 §6.3 "기존 파일 인정" 규칙이 다시 받지 않고 성공으로 기록한다.
- **받은 파일의 mtime은 보존하지 않는다** [지시 2026-09-24]. OS가 정하는 그대로(받은 시각) 둔다.
  근거: DOWNLOAD·BOTH가 쓰일 현장은 극히 적다(§0.1). 원격 mtime 보존 단계를 늘리지 않는다.

## 5. 설정

### 5.1 형태 [설계안 §10 승계]

```ini
[GENERAL]
Mode = download                 ; put(기본) | download | both(§1.2)

[DOWNLOAD]
Sites = SOCH,PALM,SUWN          ; 비우거나 키가 없으면 전체
MaxWorkers = 4

[DOWNLOAD.SFTP]
AuthMethod = publickey
Host = ...
Port = 22
User = ...
PrivateKey = ...
KnownHosts = ...
StallTimeoutSeconds = 30

[DOWNLOAD.RINEX2_HOURLY]
RemotePath = /RINEX2/(YYYY)/(DOY)/          ; 원본. 날짜 토큰만. 아래 (HH) 폴더는 재귀가 수집
LocalPath  = D:\RNX\(YYYY)\(DOY)\(SITE)\    ; 목적지. (SITE)·(HH) 허용
```

- `[DOWNLOAD.SFTP]`는 기존 `SFTPConfig` 구조체를 그대로 쓴다. 방향별로 둔 이유는 원래부터
  "BOTH에서 송신·수신 서버가 다를 수 있어서"다(`config.go` 주석).
- `[SCAN]`(ScanRecentDays·ScanDays·DeepScanHour), `[INGRESS] GraceSeconds`, `[LEDGER]`, `[LOG]`는 PUT과 공유한다. [판단]
- Category는 섹션 이름이 정한다. 파일명에서 추론하지 않는다 (PATH v3 §2-A와 같은 규칙).
- `config.example.ini`의 `[DOWNLOAD*]` 예시는 주석 처리된 선택 블록으로 둔다. PUT 현장이 템플릿을 복사해도 DOWNLOAD가 켜지지 않는다.

### 5.2 시작 검증 (모두 시작 단계 거부)

| # | 조건 | 근거 |
|---|---|---|
| 1 | `Mode=download`인데 `[DOWNLOAD.*]` 카테고리 섹션이 없음 | |
| 2 | RemotePath에 `(SITE)`·`(HH)` | 원본 파일명 토큰은 PATH v4 (§1.2) |
| 3 | Daily 카테고리 LocalPath에 `(HH)` | 추출할 수 없는 토큰 (결정 문서 §4.3-4) |
| 4 | `[PUT.*]` 경로에 `(SITE)`·`(HH)` | PUT 적용은 PATH v4. 조용히 무시하지 않는다 |
| 5 | `Sites` 값 파싱 실패 | `domain.ParseSiteList` 재사용 |
| 6 | `Mode=both` (운영 개방 전까지) | 기존 `downloadImplemented` 게이트를 방향별로 나눈다 |

## 6. DOWNLOAD 판정

### 6.1 원격 Ingress (②): `verify.Verifier` 재사용

`scan.Entry → verify.Input` 변환은 PUT처럼 조립자(download)가 한다. 거부 사유와 집계도 PUT과 같다.

| 사유 | 의미 |
|---|---|
| PartFile | `.part`·`.filepart` 등 임시 이름 — 상대가 올리는 중 |
| Zero | 0바이트 |
| Grace | 원격 mtime이 `GraceSeconds` 안 — 상대가 올리는 중일 수 있음 |
| FutureMTime | 원격 시계가 앞섬 — 운영자 확인 신호 |
| Mismatch | 섹션 카테고리와 파일명이 함의하는 버전·주기 불일치 |

- [미결] 중계 서버에 쓰는 쪽이 임시 이름 → Rename 방식이면 PartFile만으로 충분하고 Grace는 0으로 둘 수 있다.
  원격 서버와 로컬 PC의 시계 차이가 크면 Grace·FutureMTime 판정이 흔들린다. 현장 확인 후 기본값을 정한다.

### 6.2 관측소 (③)

| 상황 | 처리 |
|---|---|
| `Sites` 지정, 파일 관측소가 목록에 없음 | 제외. `excluded_site` 집계 |
| 관측소 식별 불가 (`SiteFromName` ok=false) + (`Sites` 지정 또는 LocalPath에 `(SITE)`) | 제외. `unidentified` 집계 (resend 정책과 동일) |
| LocalPath에 `(HH)`, 시각 추출 불가 | 제외. `unidentified` 집계 |

- 관측소 규칙은 `domain.ParseSiteList`·`SiteFromName` 그대로다. 정확 일치, 대문자 정규화.
- `(HH)` 추출: RINEX2 Hourly는 세션 문자 `a`~`x` → `00`~`23`. RINEX3/4는 시작 시각 필드 `YYYYDDDHHMM`의 `HH`.
  추출 함수는 `domain`에 둔다 (파일명 파생의 주인은 domain 하나).

### 6.3 받을지 판정 (④)

판정 재료는 **download 자신의 수신 기록과 로컬 파일**뿐이다 (원칙 7). PUT DB는 보지 않는다.

**1단계: 수신 기록**

| 수신 기록 | 처리 |
|---|---|
| 성공, 원격 size·mtime 같음 | 건너뜀 (이미 받음) |
| 성공, 원격 size·mtime 다름 | 받기 (원격 재생성, 우리가 받은 파일이므로 덮어쓴다) |
| 없음 / 실패 | 2단계 |

**2단계: 로컬 최종 경로** (`backup_RNX*.py`의 "있으면 건너뜀"과 같은 발상)

| 로컬 최종 파일 | 처리 |
|---|---|
| 없음 | 받기 |
| 있고 크기 == 원격 크기 | **받지 않고 인정.** 성공으로 기록, `adopted` 집계. ⑦~⑧ 사이 중단의 복구이자, 파이썬 스크립트가 이미 받아 둔 파일을 그대로 인정하는 경로다 |
| 있고 크기 다름 | 건너뜀. `skipped_exists` 집계 (원칙 3: 우리가 받지 않은 파일은 덮어쓰지 않는다) |

- 로컬 최종 파일이 사라졌더라도 성공 기록이 있으면 다시 받지 않는다. 다시 받아야 하면 후속 수동 재수신 CLI가 담당한다.
- 크기만 같고 내용이 다른 경우는 인정해 버린다. 안정적인 내부 서버에서 같은 이름·같은 크기의 다른 내용은 상정하지 않는다 (원칙 6).
- 이전 설계의 "common origin=LOCAL이면 건너뜀"은 뺐다. download가 PUT DB를 보지 않는다는 원칙 7 때문이며,
  이 PC의 원본 파일은 2단계의 "있고 크기 다름 → 덮어쓰지 않음"과 "같으면 인정(받지 않음)"으로 보호된다.

## 7. 전송 (⑤~⑧)

| 단계 | 내용 |
|---|---|
| 원격 읽기 | `transport.SFTPFS`에 원격 파일 읽기 메서드 1개 추가. 기존 StallTimeout 감시(UNIT3)가 그대로 적용된다 |
| 로컬 쓰기 | `transport.LocalFS`의 `EnsureDir`·`Rename`·`Remove` 재사용. `.part` 이름은 `최종이름.part` |
| 검증 | 로컬 `.part` 크기 == 원격 Entry 크기. 불일치 = 실패, `.part` 삭제 |
| 실패 | 해당 파일만 실패 + 원인. 회차 안에서 재시도하지 않고 다음 회차가 다시 받는다 |
| 병렬 | `[DOWNLOAD] MaxWorkers` bounded pool. 장부 쓰기는 PUT과 같은 단일 Writer 규약 |

**PUT에서 가져오지 않는 것** (원칙 6):

| PUT 장치 | DOWNLOAD에서 빼는 이유 |
|---|---|
| IN_PROGRESS 기록 + 시작 시 회수 | 결과만 기록한다. 끊기면 다음 회차가 다시 받고, `.part`는 덮어써진다 (§4) |
| PENDING 선등록 | 세트 게이트 등 PUT 전용 요구에서 온 상태다 |
| 해시 계산·기록 | mtime 드리프트 재전송 사고(불안정한 기관 서버)에서 온 장치다. 받는 쪽은 원격 size·mtime으로 충분하다 |
| revision별 이력 누적 | 파일당 결과 하나면 된다. 과거 수신 이력은 로그로 충분하다 |
| attempts 누적 | 실패 원인 하나면 된다 |

transport는 방향을 모른다는 원칙(지침 §15)은 유지된다. 추가 메서드는 "원격 파일 하나를 읽기용으로 연다"일 뿐이다.

## 8. 과제 1: DB 설계 [결정 2026-09-24]

> **DB 구조(컬럼·타입)는 이 문서에서 정하지 않는다.** 별도 문서 `docs/db/SFTPClient_DB_DESIGN_v1.md`에서
> 개념 설계 → 논리 설계 → 물리 설계 순으로 확정하고, 그 전에 구현을 시작하지 않는다.

### 8.1 배경

현재 DB(schema.sql v9, schema_version 6)는 개념 설계 없이 PUT 구현과 함께 만들어졌다.
DOWNLOAD를 붙이려 할 때마다 "common이 무엇인가"가 흔들린 원인이 여기에 있다.
§3의 결정(결합도 최소, put 기존 그대로)으로 범위가 정해졌으므로, DB 설계는 **download 기록을 PUT DB와 섞지 않고 세우는 일**이 된다.

### 8.2 이미 정해진 전제

| # | 전제 | 근거 |
|---|---|---|
| 1 | **PUT DB(common_ledger·put_ledger·schema_meta)는 구조·동작·버전을 바꾸지 않는다** | 원칙 4, §0.1-1 |
| 2 | download는 PUT DB를 읽지도 쓰지도 않는다 | 원칙 7 |
| 3 | common은 DB를 갖지 않고 읽지도 않는다 | §3.1 |
| 4 | download 기록은 결과만 담는다 (원칙 6, §6.3·§7) | 판단 재료: 원격 size·mtime, 성공/실패 |

### 8.3 설계가 답해야 할 질문

| # | 질문 | 추천·메모 |
|---|---|---|
| Q1 | download 기록을 **어디에** 두는가. (a) 기존 `rinex_ledger.db` 안의 독립 테이블 (b) **별도 DB 파일** | **(b) 추천.** PUT 현장 DB에 빈 테이블도 생기지 않는다(§0.1-1). schema_version·마이그레이션 논의가 필요 없다. 결합도가 가장 낮다 |
| Q2 | 한 줄의 단위와 키 | 파일당 한 줄, `(category, 정규화 파일명)`. 정규화 규칙은 `domain` 것을 그대로 쓴다 |
| Q3 | 담을 사실 | 원격 size·mtime, 결과(성공/실패), 저장 위치, 기록 시각, 실패 원인. 그 이상은 원칙 6으로 넣지 않는다 |
| Q4 | 잠금 | 파일이 둘이어도 실행 잠금은 인스턴스당 하나(기존 lock)로 BOTH 전체를 감싼다 |
| Q5 | 보존·정리 | 기록 시각 기준. `RetentionDays > ScanDays`는 DOWNLOAD에도 필요하다. 구현은 Retention Cleanup과 함께 |
| Q6 | 식별 규칙 변경 방어 | PUT의 `schema_meta.identity_rule` 같은 장치가 download 쪽에도 필요한가 (정규화 규칙을 공유하므로) |
| Q7 | 운영 조회 | **[결정 2026-09-24] 내역서는 저장하지 않고 조회로 만든다.** 운영 조회 명령이 파일명으로 수신 기록과 put_ledger를 나란히 읽어 "어디서 받아 어디에 저장했고, 어디로 보냈고, 잘 보냈는가"를 한 장으로 보여 준다. 읽기 전용이며 어떤 판단에도 쓰지 않는다. 같은 사실을 두 곳에 저장하지 않고(하나의 사실, 하나의 주인), download·put·common의 결합도도 올리지 않는다 |

### 8.4 PUT DB의 현재 개념 정리 (같은 문서에 기록)

PUT DB는 바꾸지 않지만, 개념 설계 없이 만들어진 것을 **사후 개념 문서로 정리**한다.
DOWNLOAD 논의에서 드러난 오해의 원인을 문서로 남겨 다시 흔들리지 않게 하기 위해서다.

| 항목 | 정리할 내용 |
|---|---|
| `common_ledger`의 실제 성격 | 이름은 common이지만 **PUT의 관측·판단 테이블**이다 (변경 판정, revision, 세트 게이트, Ping-Pong용 origin) |
| common 모듈과의 관계 | 새 구조의 common(조율자)과 **무관하다**. 이름이 같을 뿐이다. 이름 변경은 운영 DB 전환이 필요하므로 하지 않는다 |
| `origin`·`RepostDownloaded` | download가 PUT DB에 쓰지 않으므로 미사용. 코드는 그대로 두고 문서에 미사용으로 표기 |

## 9. BOTH

[설계안 §4.1] **DOWNLOAD 처리 → PUT 처리.** 새 구조에서는 §3 그대로다.

| 항목 | 결정 |
|---|---|
| 조율 | common = `cmd`의 얇은 조립. 한 잠금 안에서 `download.Run` → `put.Run` |
| DOWNLOAD 실패 | 받은 만큼만 put이 본다. DOWNLOAD 실패가 put을 막지 않는다 [판단]. 종료 코드는 둘 중 나쁜 쪽 |
| 중계 구성 | 타겟 폴더(DOWNLOAD LocalPath)를 PUT LocalPath 아래에 둔다. 그게 전부다 (§3.3 "폴더 배치가 곧 의도") |
| Ping-Pong | §3.2의 시작 검사 하나 |

BOTH 없이도 올인원은 성립한다. 같은 exe가 `Mode=put`과 `Mode=download`를 모두 갖고, 설정으로 고른다.
두 모드를 따로 예약 실행해도 된다. 그 경우 common이 끼지 않으므로 §3.2 검사가 돌지 않는다. 중계라면 BOTH를 권한다.

## 10. 보고·로그

PUT 요약과 같은 형식에 DOWNLOAD 집계를 더한다. 메시지·종료 코드는 `MESSAGES_AND_EXIT_CODES_v2` 규칙을 따른다.

```
[DOWNLOAD] listed=412 downloaded=37 adopted=0 skipped_verified=361 skipped_exists=0
           excluded_site=12 unidentified=2 rejected: part=0 grace=3 zero=0 mismatch=0 future=0 failed=0
```

- `failed>0` → 부분 실패 종료 코드 (PUT과 같은 값).
- 잠금을 잡은 모드를 로그에 남긴다 (결정 문서 §6-4).
- `Mode=put` 실행의 로그·요약은 지금과 같다 (원칙 4-1).
