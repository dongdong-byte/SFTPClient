## 0. 요약 — 2026-09-16 현재 기준

```ini
[GENERAL]
LockStaleSeconds = 10800 ; lock stale 문턱(초). 크롤링 최대 지연 3h 버스트 덮음 (14절)

[SCAN]
ScanRecentDays  = 2      ; Hot Scan.  매시간
ScanDays        = 7      ; Deep Scan. 하루 1회
UseDirMtimeSkip = false

[INGRESS]
GraceSeconds    = 60

[LEDGER]
RetentionDays   = 30     ; Ledger 재발견 안전 기준. 서울시·측위원 현장 운영값

[LOG]
RetentionDays   = 30     ; 로그 보존기간. 값은 같지만 Ledger 보존과 별개
```

**현재 경로 방향** — 로컬은 설정 루트 아래를 범위 제한 재귀 탐색하고,
발견한 파일은 RINEX 버전별 고정 평면 `RemotePath`로 전송한다.
로컬 하위 디렉터리 구조를 원격에 복제하거나 파일 날짜·시각으로 원격 경로를
계산하지 않는다.

```
RINEX2 → D:\incoming\RNX2\
RINEX3 → D:\incoming\RNX3\
```

현재 코드의 `HourLayout=dir/flat`과 `(HH)` 00~23 계산은 서울시 평면 Hourly
경로를 급히 지원하기 위해 추가한 과도기 구현이다. MVP2에서 제거한다.
Hourly `(HH)` 필수 검증을 재강화하지 않는다.
재귀 시작점·최대 깊이·날짜 범위 적용·권한 오류·symbolic link/junction 정책은
Linux OS 버전과 실제 경로를 받은 뒤 확정하며, 이 문서에서 먼저 추측하지 않는다.
Linux 배포·테스트는 MVP2 범위이나, Linux 전용 추가 보안은 공식 보안점검에서
구체적인 요구가 나온 경우에만 그 범위에 맞춰 적용한다.

```
RINEXClient.exe resend --from 2026-06-01 --to 2026-06-15 --dry-run  ; 잠정 예시
RINEXClient.exe resend --from 2026-06-01 --to 2026-06-15            ; 잠정 예시
RINEXClient.exe --dry-run                       ; 전송 없이 규모 보고
RINEXClient.exe seed --days 7                   ; 원격 나열 기준 전환 시딩 (8절)
```

`resend`라는 명령 이름과 세트 게이트 우회는 확정했지만 세부 인자는 아직 설계 전이다.
위 `--from`/`--to`/`--dry-run`은 기존 제안을 옮긴 잠정 예시이지 CLI 계약이 아니다.

용어를 다음처럼 분리한다.

- `Recover`: 시작 시 `IN_PROGRESS`를 `FAILED`로 회수하는 자동 크래시 복구
- `resend`: 운영자가 기간·대상을 지정하는 수동 재전송
- Deep Scan: 늦게 유입된 파일을 최근 `ScanDays` 범위에서 다시 찾는 자동 탐색

**추가된 DB 없음. 추가된 테이블 없음.**

**현재 스키마 원본** — `internal/ledger/schema.sql` (설계 개정 v8,
`schema_meta.schema_version = 5`). `common_ledger.local_path`는 과거 v5 설계에서
삭제되었다. 6절 참조.

## 1. 문제 — "원본을 무엇으로 아는가"

### 제기된 의문

장부와 대조해 누락을 찾는다고 했는데, **대조할 원본 목록을 프로그램이 어떻게 아는가.**

### 확인된 사실

장부에는 기대 목록(manifest)이 없다. 장부는 "있어야 할 것"이 아니라
**"본 것"의 기록**이다. 원본은 로컬 파일시스템 그 자체다.

따라서 "누락"이라는 말이 세 가지를 뭉뚱그리고 있었다.

| | 무엇인가 | 탐지 가능 여부 |
|---|---|---|
| **A** | 로컬에 있는데 아직 못 보냄 | 가능 — 장부와의 차집합 |
| **B** | 보냈는데 그 후 내용이 바뀜 | 가능 — `revision` |
| **C** | 관측소가 파일을 아예 만들지 않음 | **불가능** |

설계안 11절의 "누락 파일"은 A를 가리킨다.
원문이 "**Ledger에 없는 신규 파일**을 자동 복구 대상으로 포함한다" 이다.
13.2 의 "누락 0건" 도 BNC 로 생성 개수를 아는 **시험 조건**에서의 대조지
운영 중 기능이 아니다.

### 결정

**C 는 이번 범위에 넣지 않는다.** 설계안이 애초에 다루지 않는 항목이다.

넣게 될 경우에도 관측소 목록을 `config.ini` 에 두지 않는다.
`file_name` 앞 4글자를 `DISTINCT` 로 뽑으면 그것이 관측소 목록이다.

- 신규 관측소 → 첫 파일 유입 → 장부 등록 → 다음날부터 자동 포함
- 폐지 관측소 → N일간 관측 없음 → 자동 제외
- **설정 파일을 고칠 일이 없다**

신규 관측소는 첫날 하루 지연이 생기나, 첫날은 비교 기준 자체가 없으므로 문제가 아니다.

전송 파이프라인이 아니라 **조회 명령**(설계안 9.2 `db status` 계열)으로 분리하며,
현재 구현 범위에서 제외한다. 특히 세트 보류 리포트는 대표 확인 결과 보안 취약점
우려가 있어 구현하지 않는다. Scan 요약과 오류 로그는 전송 관측에 필요하므로 유지한다.
이름도 "누락"이 아니라 **결측 리포트**로 구분한다.

### 보강 — 크롤링 매트릭스와의 대조 (2026-08-28 추가)

`상시관측소_현황_누적.xlsx` 를 확인한 결과,
관측소 × 날짜 × (일단위 1 + 시간단위 24) 의 0/1 격자가 이미 존재한다.
8개 기관 230개 관측소, 8일 롤링이며 `_연결` 시트에 관측소별
일간 상태(양호/불량/지연/미등록)가 함께 있다.

**다만 이 파일은 정답지가 아니다.**
크롤러가 보는 곳은 gnssdata 홈페이지, 즉 **체인의 맨 끝**이다.
우리 전송 지점과 그 사이에 홉이 여럿 있고, 홈페이지 자체의 문제도 관측된다
(10.5 국립해양측위정보원 사례 참조).
**따라서 프로그램이 이 파일을 읽어 판단하도록 만들지 않는다.**
크롤러는 지금처럼 별도 도구로 유지한다.

**그러나 장부와 짝지으면 원인 분리가 가능해진다.**

| 장부 | 매트릭스 | 해석 |
|---|---|---|
| 보냄 | 있음 | 정상 |
| **보냄** | **없음** | **하류 문제.** 우리 구간은 정상 — 수신측 처리 또는 게시 |
| **안 보냄** | **있음** | 다른 송신자 존재(전환기) 또는 우리 스캔 누락 |
| 안 보냄 | 없음 | 원본이 애초에 생성되지 않음 (C) |

현재는 왼쪽 열이 없어 매트릭스의 0 이 홈페이지 문제인지 전송 문제인지
관측 문제인지 구분되지 않는다. 장부가 그것을 가른다.

C 탐지는 이 대조로 접근 가능하나, 정답지가 아니므로 **추정이지 판정은 아니다.**
프로그램 변경은 필요 없다.

> **미확인** — RINEX2 는 파일명의 시각이 문자 코드(`a`~`x`)라
> `substr` 방식이 그대로 적용되지 않는다. 별도 처리가 필요하다.

## 2. 문제 — DOWNLOAD 의 구조를 잘못 이해하고 있었다

### 제기된 의문

논의 중 DOWNLOAD 를 **"수신기에 접속해 데이터를 긁어온다"**로 전제하고 있었으나
실제 구조가 다르다.

### 확인된 사실

```
[Alloy 수신기]  --push-->  [서버 A]  --우리 프로그램-->  [중간서버 B]  -->  [최종 C]
     ↑                                      ↑
  전송경로를 여기서 설정              여기서부터가 우리 범위
```

수신기가 **밀어 넣는다.** 우리 프로그램은 수신기와 대화하지 않는다.

따라서 PUT 과 DOWNLOAD 는 같은 전송이며, **프로그램을 어느 쪽에 설치했느냐**만 다르다.

| 설치 위치 | 방향 | origin |
|---|---|---|
| 서버 A | PUT | LOCAL |
| 서버 B | DOWNLOAD | DOWNLOAD |
| 중간서버 (A→B→C) | BOTH | DOWNLOAD → 재PUT |

### 파생 결론 1 — PUT 우선 개발이 옳다

설계안이 download → put 순서였던 것은 측위원처럼 **중간서버가 있는 구성**을
먼저 상정했기 때문이다. 순서가 틀렸던 것이 아니라
**어느 서버에 먼저 설치하느냐**가 달랐다.

지리원은 수신기가 파일을 떨구는 폴더에서 바로 전송하는 단일 홉 구조이므로
**PUT 만으로 서비스가 성립한다.**

### 파생 결론 2 — DOWNLOAD 가 필요한 조건은 하나뿐이다

> **원본 서버에 우리 프로그램을 설치할 수 없을 때.**

측위원 이중 구조도 A 와 B 양쪽에 설치할 수 있다면 **PUT 두 번**으로 풀린다.
타 기관 소유라 접근권이 없거나 정책상 설치가 불가한 경우에만 "당겨오기"가 필요하다.

> **미확인** — 측위원 중간서버에 프로그램 설치가 가능한지.
> 가능하다면 현재 알려진 어느 기관에도 DOWNLOAD 가 필요하지 않다.

### 파생 결론 3 — 올인원 요구는 이미 충족된다

대표 요구는 "PUT 과 DOWNLOAD 가 동시에 돈다"가 아니라 **배포 단위가 하나**라는 뜻이다.
설계안 19절의 "하나의 배포 단위에서 제공한다"와 같은 말이다.

```
RINEXClient.exe 하나 → config.ini 의 Mode 로 역할 결정
```

**PUT 만 먼저 완성해도 올인원 요구를 위배하지 않는다.**

### 결정

DOWNLOAD 관련 구조물(`origin` 컬럼, `RepostDownloaded`, `download_ledger`)은
**유지한다.** 빼는 비용이 두는 비용보다 크다. 행이 안 생기면 용량도 쓰지 않는다.

**2026-09-15 일정 결정:** DOWNLOAD와 `download_ledger` 구현은 MVP3으로 연기한다.
MVP2는 세트 원자성, `resend`, 경로 범용화, Linux 배포·테스트,
Retention Cleanup을 다룬다. 이 절의 DOWNLOAD 분석은 향후 설계 근거로 보존한다.

## 3. 문제 — 0KB 파일은 실제로 발생하는가

### 제기된 의문

BNC·수신기는 파일을 생성하는 쪽이라 append 가 일어나지만,
**우리 서버는 완성된 파일을 전송받는 구조**다.
그렇다면 0KB 후 커지는 현상이 실제로 있는가.
그리고 "생성이 멈췄다"를 무엇으로 표현하는가.

### 확인된 사실

현상은 남되 **원인과 지속시간이 다르다.**

| | 무엇이 일어나는가 | 지속 시간 |
|---|---|---|
| BNC / 수신기 자체 | 관측하며 append | **1시간~하루** |
| **우리 서버** | 수신기가 완성본을 전송하는 중 | **수 초~수 분** |

파일이 우리 서버에 처음 나타나는 순간은 **전송 시작 시점**이다.
그 짧은 구간에 스캔이 걸리면 0KB 또는 절반짜리로 보인다.

### 결정 1 — Grace Time 무용론을 철회한다

CONCEPT 4.4 는 이렇게 적고 있었다.

> Grace Time 은 정확성 장치가 아니라 헛전송을 줄이는 장치이다.
> 쓰기 사이의 공백이 Grace Time 보다 길면 미완성 파일이 그대로 통과한다.
> 그 공백의 최대치는 알 수 없다.

이는 **append 형을 전제로 한 판단**이었다.
전송 중 파일은 연속으로 흘러들어오고 끝나면 mtime 이 고정된다.
쓰기 사이 공백이 네트워크 지연 수준이므로 **`GraceSeconds = 60` 이 실질적으로 작동한다.**

"알 수 없는 값"이 **"계산 가능한 값"으로 승격된다.**

CONCEPT 4.4 의 해당 서술을 이 내용으로 갱신할 것.

### 결정 2 — "생성이 멈췄다"의 판정 수단 3계층

| | 수단 | 성격 | 플랫폼 |
|---|---|---|---|
| 1 | `now - mtime > GraceSeconds` | 추정 | 공통 |
| 2 | **파일 잠금 검사** | **사실 판정** | Windows 만 |
| 3 | `revision` | 최후 회수 | 공통 |

2번은 Windows 가 쓰기 중인 파일의 핸들을 잡고 있다는 성질을 이용한다.
공유 모드 없이 여는 시도가 실패하면 누군가 쓰는 중이다.

```go
type WriteDetector interface {
    IsBeingWritten(path string) (bool, error)
}
// inuse_windows.go — CreateFile(dwShareMode=0) 잠금 검사
// inuse_other.go   — 항상 false. mtime grace 에 위임
```

`security` 패키지의 DPAPI 처리와 같은 빌드태그 구조를 쓴다.

> **미확인** — Linux 는 강제 잠금이 없어 이 수단을 쓸 수 없다 (MVP2 Linux 단계).
> SAN/SMB 뒤에 있을 때의 동작도 실측이 필요하다.

### 결정 3 — revision 의 근거가 더 강해졌다

전송 구조에서 새로 생기는 경로가 있다.

```
전송 시작 → 중간에 네트워크 끊김 → 절반짜리 파일이 남음
  → 더 이상 안 커지므로 Grace Time 통과 → 전송해버림
  → 수신기가 재시도해 완전한 파일로 덮어씀
  → 크기 변경 감지 → revision 2 → 재전송            ← 회수
```

**전송 실패 후 재시도는 관측 재생성보다 훨씬 흔하다.**
끊긴 파일은 실제로 안 커지므로 Grace Time 으로는 원리적으로 막을 수 없다.
`revision` 이 정확성의 주인이라는 판단은 유지된다.

> **미확인 — 확인 우선순위 높음**
> 수신기가 임시 이름으로 쓴 뒤 rename 하는가.
>
> | | 결과 |
> |---|---|
> | 임시명 후 rename | 미완성 파일이 아예 안 보임. Ingress 가 크게 단순해짐 |
> | 최종명으로 직접 씀 | 위 3계층이 모두 필요 |
>
> `--dry-run` 으로 디렉터리를 나열해 `.part` `.tmp` `.filepart` 가 섞여 나오는지 보면 판별된다.
> 어느 쪽이든 `size > 0` 과 `revision` 은 남긴다. 기관마다 수신기 설정이 다를 수 있다.

## 4. 문제 — 8일 이상 늦게 밀려 들어온 데이터를 감지할 수 있는가

### 제기된 의문

지리원에서 캐스터를 재시작하면 그동안 안 들어오던 데이터가 밀려 들어온다.
스캔이 7일치뿐이라면 8일 방치 후 복구된 데이터는 영영 못 잡는 것 아닌가.

### 확인된 사실

**잡지 못한다.** 디렉터리가 도착 시각이 아니라 **관측 시각**으로 정해지기 때문이다.

```
오늘(240일) 밀려 들어온 232일 관측 파일
  → E:\RINEX-V3-H\2026\232\14\  에 놓임
  → Hot Scan(2일), Deep Scan(7일) 모두 그 디렉터리를 열지 않음
```

파일은 오늘 생겼는데 8일 전 서랍을 안 연다.

**이는 장부가 만든 문제가 아니다.** 장부는 물어보면 정확히 답한다.
문제는 스캐너가 애초에 안 물어본 것이다. **고칠 곳은 스캐너다.**

### 기각한 안 — DB / 테이블 추가

새 테이블을 만들어도 **거기 넣을 데이터를 스캐너가 못 가져온다.**
안 열어본 디렉터리의 정보는 어느 DB 에도 들어가지 않는다.
`scan_state` 테이블을 기각했던 것과 같은 이유다.

### 기각한 안 — Deep Scan 상한 제거 + 디렉터리 mtime 필터

한때 채택 방향으로 검토했던 안이다. 근거는 명확했다.

| 디렉터리에서 일어난 일 | 디렉터리 mtime |
|---|---|
| 기존 파일에 append | 안 바뀜 |
| **새 파일 생성** | **바뀜** ← 백필이 이것 |

또한 사람이 복사로 복구할 때 **파일 mtime 은 원본이 보존되지만
디렉터리 mtime 은 보존되지 않는다.** 파일 mtime 으로는 운영자 `resend`를 잡을 수 없고
디렉터리 mtime 으로는 잡을 수 있다.

**그러나 로컬 디스크에 3년치가 보관된다는 사실이 확인되면서 기각했다.**

1. **장부가 디스크 보존기간보다 길어야 한다는 불변식이 깨진다.**
   3년치면 장부도 3년, 약 4GB(3형태면 12GB). 1시간마다 도는 프로그램이
   들고 다닐 장부가 아니다.
2. **디렉터리 mtime 은 파일 삭제 시에도 갱신된다.**
   3년치를 보관하면 어딘가에서 정리 작업이 돈다. 그때마다 오래된 디렉터리
   mtime 이 갱신되어 스캐너가 진입하고, 장부에 없는 파일들이 **전량 재전송된다.**
3. 30일 통째 스캔 비용은 **하루 1회 5초**다. 5초 아끼자고 재전송 사고를 감수할 이유가 없다.

`UseDirMtimeSkip = false` 를 유지하며, 이 근거를 주석에 남긴다.
설계안 11.1 이 든 이유(네트워크 스토리지 부정확)보다 이쪽이 더 직접적이다.

### 기각한 안 — Deep Scan 30일

"사람이 7일 이후에 복구할 확률이 높으니 넉넉하게 30일" 이라는 안이었다.

**추정 위에 임의의 숫자를 얹은 것**이라 기각했다.
45일 뒤 복구하는 사람이 있으면 그대로 뚫리고, 그럼 60으로 늘리자는 이야기가 나온다.
끝이 없다.

### 채택 — 3갈래 분리

```
[자동 · 정상운영]
  Hot Scan       최근 2일   매시간    정상 유입, 전송 중 파일 성장
  Deep Scan      최근 7일   하루 1회  늦게 유입된 일반 누락 회수

[수동 · 운영자 재전송]
  resend         기간 고정 안 함
                 운영자가 장애 기간·대상 지정 → 해당 구간을 재탐색·재전송
                 → 자동 파이프라인의 세트 게이트는 우회
```

**상한을 정하려 하지 않고, "그건 사람이 아는 일"이라고 인정한 뒤 입력받는 구조다.**
`resend`는 사람이 한 일이고, 그 사람은 자기가 무엇을 했는지 안다.

30일안과 비교하면 범위를 줄였는데 커버리지는 넓어졌다.

| | 30일안 | 3갈래안 |
|---|---|---|
| Deep Scan 파일 대조 | 매일 18만 | **매일 4.2만** |
| 장부 보존 | 120일 (440MB) | **30일 (110MB, 당시 추정 기준)** |
| 30일 초과 백필 | 못 잡음 | **잡음** |

과거에는 `scan` 패키지에 Hot / Deep / Recovery 날짜 범위만 다르게 넣는 구조를
상정했다. 현재는 수동 재전송을 `resend` 명령으로 분리했으며, 정확한 Scan 재사용
경계와 Ledger 처리 방식은 `resend` 설계 시 확정한다.

### 부수 결정

- Deep Scan 이 도는 시각에는 Hot Scan 을 건너뛴다 (7일이 2일을 포함)
- `resend` 는 dry-run을 지원하는 방향으로 설계한다. 날짜 오타 방지
- `resend` 실행 중에는 정기 실행과 `lock` 을 공유한다.
  오래 걸리는 명령이라 겹치면 같은 파일을 두 프로세스가 전송한다.
  stale 문턱은 `[GENERAL] LockStaleSeconds` (14절).

> **미확인** — "사람이 7일 이후에 복구할 확률이 높다"는 추정은 그대로 남아 있다.
> 이를 데이터로 대체하기 위해 Deep Scan 로그에 `oldest_new` 를 남긴다.
>
> ```
> [DEEPSCAN] dirs=336 files=42000 new=340 oldest_new=2026-08-23 (5일 전)
> ```
>
> 한 달 운영하면 분포가 나온다. 대부분 3일 이내면 `ScanDays` 를 줄여도 되고,
> 7일에 붙어 잘리는 것이 보이면 늘려야 한다는 증거다.

## 5. 검토 — 장부 보존기간과 `resend`의 관계

### 제기된 의문

(3갈래안 검토 중 도출) "Ledger 가 신규/변경만 판별한다"는 전제는
**장부가 그 기간을 기억하고 있을 때만** 성립한다.

### 확인된 사실

디스크에 3년치가 있고 장부가 30일치만 들고 있으면:

```
resend --from 2026-02-01 --to 2026-02-28   # 잠정 예시
  → 그 구간 파일이 장부에 없음 → 전부 "신규" 판정
  → 2월 한 달치 전량 재전송        ← 이미 다 보낸 파일들
```

### 당시 설계안 — 최종 의미론 결정 필요

`resend`가 일반 Scan처럼 Ledger 판정을 재사용하는 방식이라면
**`LedgerRetentionDays`가 안전 범위의 실질 상한**이 된다. 반대로 지정 범위 전체를
강제로 다시 보내는 명령이라면 Ledger 보존기간은 후보 판정의 상한이 아니다.
두 방식 중 무엇을 채택할지는 MVP2 `resend` 구현 전에 결정한다.

초기 설계에서는 60일을 채택했으나, 2026-09-16에 **30일**로 변경한다.
서울시·측위원 현장 배포에서 실제로 1개월 보존을 적용한 운영 경험이 근거다.
설정은 달력 월이 아니라 고정 일수이므로 `RetentionDays = 30`으로 표현한다.

| `RetentionDays` | 행 수 | 용량 |
|---|---|---|
| 180일 | 약 108만 | 약 660MB |
| **30일** | **약 18만** | **약 110MB** |

행당 약 620B 로 계산했다 (`common_ledger` 본체+인덱스 315B,
`put_ledger` 본체+인덱스 230B, 페이지 여유 포함).

**주의 — `DELETE` 로는 파일 크기가 줄지 않는다.** SQLite 는 free page 를
재사용할 뿐 OS 에 반환하지 않는다. 위 추정 조건에서는 약 110MB에서 평형을 이룬다.
줄이려면 `VACUUM` 이 필요하고 그동안 DB 전체가 잠긴다.

### 검토한 안전장치 — 미확정

```
$ RINEXClient.exe resend --from 2026-02-01   # 잠정 예시

거부: 지정 구간이 장부 보존범위(30일) 밖입니다.
      장부 최초 기록: 2026-06-29
      이 구간을 실행하면 약 42,000개가 재전송될 수 있습니다.
      의도한 것이라면 --force 를 붙이십시오.
```

되돌릴 수 없는 명령이므로 문턱을 둔다.
정확한 플래그와 `--force` 제공 여부는 아직 확정하지 않았으며 `resend` 설계에서 결정한다.

### config 검증에 추가할 항목

```
LedgerRetentionDays > ScanDays     ; 깨지면 시작 시 거부
```

짧으면 **장부에서만 지워진 파일**이 신규로 판정되어 재전송된다.
중복 전송이 정확히 이 경로로 돌아온다.

> **미확인** — 3형태(`.rnx` / `.crx` / `.crx.gz`) 유입이 확인되면
> 30일이어도 파일 형태 수에 따라 추정 용량이 크게 달라진다. `--dry-run` 결과로 확인 후 재검토한다.

### 2026-09-16 구현 상태 — 설정만 있고 실제 삭제는 없다

`[LEDGER] RetentionDays = 30`과 `RetentionDays > ScanDays` 시작 검증은 구현됐다.
그러나 `cmd/rinexclient/main.go`에는 Deep Scan 뒤 Cleanup이 TODO로 남아 있어,
현재 실행파일은 30일이 지나도 `common_ledger`와 연결된 `put_ledger` 행을
자동 삭제하지 않는다.

`[LOG] RetentionDays = 30`은 로그 보존 설정이며 DB 행 삭제와 무관하다.
현재 저장소에는 로그 보존 정리를 수행하는 `internal/logging` 구현도 없다.
이 절의 DB 검증 대상은 `[LEDGER] RetentionDays = 30`이다.

MVP2에서 다음을 구현·검증한다.

- 성공한 Deep Scan 뒤 `ingress_verified_at < now - RetentionDays`인 common 행 삭제
- FK `ON DELETE CASCADE`에 의한 관련 put 행 삭제
- 정확한 30일 경계의 포함/제외와 최근 행 보존
- Cleanup 실패 처리
- SQLite free page 재사용 유지, 정기 `VACUUM` 미실행
- 재귀 Scan이 보존기간 밖의 오래된 파일을 신규로 되살려 재전송하지 않는지 검증

마지막 항목은 경로 범용화의 필수 안전조건이다. 로컬에 10년치 파일이 남아 있으므로
재귀 탐색이 무제한이면 Retention으로 지운 과거 행이 다음 Scan에서 신규가 될 수 있다.
재귀 방식은 반드시 Hot/Deep의 날짜 범위와 함께 설계한다.

## 6. 문제 — 스캔 성능이 저하되지 않는가

### 제기된 의문

지리원 120개 관측소 × 24시간 × 7일 × 4 Category 를 매번 스캔하면
성능 저하가 일어나지 않는가. 팀장도 같은 지적을 했다.

### 과거 결정 1 — 상위 폴더를 walk 하지 않는다 (2026-09-15 폐기)

```
❌ walk 방식        E:\RINEX-V3-H\ 부터 하위 전부 재귀 → 폴더 수만 개
✅ 템플릿 전개      E:\RINEX-V3-H\(YYYY)\(DOY)\(HH)\ 를 계산 → 그 폴더만
```

`pathpl` 이 존재하는 이유가 이것이다.
**보관기간이 7일이든 3년이든 스캔 비용이 늘지 않는다.**
지적된 "상위 폴더 스캔 성능" 문제는 이미 설계에서 회피되어 있다.

이 결정은 모든 기관의 날짜·시간 디렉터리 모양을 템플릿으로 정확히 표현할 수
있다는 전제에 의존했다. 서울시의 `(HH)` 없는 평면 Hourly 경로 때문에
`HourLayout`을 긴급 추가했고, 2026-09-15 지리원에도 `(HH)` 폴더가 없음을
재확인했다. 다음 Linux 설치처의 경로도 다를 가능성이 있어 이 전제는 더 이상
유지하지 않는다.

**현재 방향:** 설정한 로컬 루트를 벗어나지 않는 범위 제한 재귀 탐색으로 전환한다.
무제한 전체 디스크 walk를 채택한 것은 아니다. 재귀 시작점·깊이·날짜 범위·권한
오류·symbolic link/junction 정책은 Linux OS 버전과 실제 경로를 받은 뒤 확정한다.
Scan은 계속 순차 실행하며, 한 번에 전체 파일을 메모리에 적재하지 않는다.

### 확인된 사실 2 — 관측소별 디렉터리가 없다

한 시간 디렉터리 안에 120개 관측소 파일이 전부 들어 있다.
**120개 관측소를 120번 도는 것이 아니라 1번 나열한다.**

| | 디렉터리 나열 |
|---|---|
| Hot Scan 2일 | 약 104회 → **1초 내외** |
| Deep Scan 7일 | 약 364회 → **2초 내외** |

### 실제 위험은 나열 횟수가 아니라 파일 단위 처리

| | 위험 | 대응 |
|---|---|---|
| 파일당 `os.Stat` | Linux/SMB 에서 파일당 왕복 | Windows 는 `ReadDir` 이 크기·시각을 함께 반환하므로 `Info()` 가 무료. MVP2 Linux 단계에서 실측 |
| 파일당 DB 조회 | 4.2만 번 `SELECT` | **디렉터리 단위로 일괄 조회 후 메모리 대조** |

### 기각 — `idx_common_local_path` 추가안

한때 디렉터리 단위 일괄 조회를 위해 `local_path` 인덱스를 제안했으나,
`local_path` 컬럼 자체를 삭제하기로 하면서 **철회한다.**
없앨 컬럼에 인덱스를 거는 안이었다.

### 채택 — `common_ledger.local_path` 삭제 (스키마 v5)

**근거 (운영자 판단)**

> 장부를 만드는 것은 "완제품이 잘 받아졌는가 / 잘 보내졌는가"에 답하기 위함이다.
> 경로는 생각보다 자주 바뀐다. 통보는 오지만, 이를 DB 에 적는 순간
> 그로 인해 데이터가 중복 전송될 수 있다.

`local_path` 는 식별자가 아니라 속성이며(schema_v4 주석 172행),
장부의 존재 목적에 기여하지 않는다. 저장하면 코드가 그것에 의존하게 된다.

### 파생 결과 — 후보 선정이 DB 주도에서 스캔 주도로 바뀐다

당시 `schema_v4.sql` 초안의 후보 조회는 `local_path` 를 SELECT 하여
"무엇을 어디서 보낼지"를 DB 가 지시하는 구조였다. 컬럼을 삭제하면 성립하지 않는다.

```
기존  DB 주도    장부가 후보와 경로를 모두 제공
변경  스캔 주도  스캔이 (경로, 파일명, size, mtime) 을 이미 알고 있다
                 장부에는 "이 이름들 중 안 보낸 것이 무엇인가"만 묻는다
```

```sql
-- 디렉터리 하나를 나열한 뒤, 그 안의 파일명들로 일괄 조회
SELECT file_name, revision, size, mtime
  FROM common_ledger
 WHERE file_name IN (?, ?, ?, ...);
```

**PK 인덱스를 그대로 탄다.** 별도 인덱스가 필요 없다.
9절의 "디렉터리 단위 일괄 조회" 요구가 이것으로 충족된다.

부수 효과 — DB 주도에서는 `FAILED` 행이 스캔 범위 밖으로 밀려나도
영구히 후보로 남았으나, 스캔 주도에서는 **자연히 만료된다.**
7일이 지나면 자동 후보에서 빠지고, 필요하면 운영자가 `resend`로 명시한다.
자동 재시도와 운영자 `resend`의 경계가 명확해진다.

**`put_ledger.remote_path` 는 유지한다.** 그것은 "어디로 보냈는가"라는 이력이며,
중단 복구 시 원격 `.part` 정리에 실제로 필요하다.

### 영향 범위

| 대상 | 작업 |
|---|---|
| `internal/ledger/schema.sql` | `local_path` 컬럼 삭제와 후보 조회 주석 반영 완료 |
| `internal/ledger/common.go` | UPSERT 에서 `local_path` 제거 (작성 완료분 수정) |
| `SFTPClient_LEDGER_CONCEPT.md` | 후보 선정 서술 갱신 |

### 계측 로그를 처음부터 넣는다

현장 접근이 불가능하므로 **프로그램이 스스로 재서 알려주게 한다.**
설계안 12절이 이미 "구간별 계측"을 요구하고 있다.

```
[SCAN] cat=RINEX3_HOURLY mode=hot dirs=48 files=5760 list=1.2s ledger=0.3s total=1.5s errs=0
```

첫 실행 로그 한 장이면 위 추정이 사실로 결판난다.

> **미확인** — 원본 디렉터리가 SAN 인지 SMB 인지.
> `fsutil fsinfo drivetype E:` 로 확인 가능하다.
> `Fixed Drive` 면 SAN/로컬, `Remote/Network Drive` 면 SMB.
>
> 다만 **Windows 에서는 이 구분이 거의 의미가 없다.**
> `os.ReadDir` 이 디렉터리 열거 API 를 쓰고, 이 API 가 파일명과 함께
> 크기·수정시각을 한 번에 반환하므로 `DirEntry.Info()` 가 추가 호출을 하지 않는다.
> SMB 여도 디렉터리당 왕복 1~2회지 파일당 왕복이 아니다.
> 파일당 `lstat` 이 발생하는 것은 Linux 다 (MVP2 Linux 항목).

## 7. 문제 — Category 별로 DB 를 나누는 것이 SRP 에 맞는가

### 제기된 의문

RINEX2/3 × Daily/Hourly 4개를 각각 별도 DB(또는 테이블)로 두고
각 경로가 자기 것만 보게 하면 SRP 에 더 맞지 않는가.

### 기각 — DB 파일 4개는 기술적으로 불가능하다

취향 문제가 아니라 SQLite 제약이다.

1. **FK 가 DB 파일을 넘지 못한다.** `put_ledger.file_name` → `common_ledger.file_name`
   FK 는 같은 파일 안에서만 선언된다. CONCEPT 3.2 의 "부모 없는 송신 이력은
   있을 수 없는 상태이므로 FK 가 실제로 오류를 막는다"는 방어선이 사라진다.
2. **WAL 에서는 다중 DB 트랜잭션이 원자적이지 않다.** `ATTACH` 한 DB 간
   원자적 커밋은 WAL 이 아닐 때만 보장된다. 우리는 WAL 을 확정했다.
   `IN_PROGRESS` 전환처럼 두 테이블을 같은 트랜잭션에서 갱신하는 지점이 깨진다.

### 기각 — 테이블 4개는 가능하나 SRP 근거가 성립하지 않는다

SRP 는 **"모듈이 변경되어야 할 이유가 하나"**다.
네 테이블의 변경 이유(컬럼 추가, 제약 변경, 인덱스 변경)는 **완전히 동일하다.**
하나를 고치면 넷 다 고쳐야 한다.

**변경 이유가 하나인데 구현체가 넷인 상태이며, 이는 SRP 충족이 아니라 DRY 위반이다.**

네 테이블의 컬럼이 한 글자도 다르지 않다는 것이 신호다.
스키마가 같다는 것은 **같은 엔티티**라는 뜻이고 `category` 는 그 속성이다.
속성값이 다르다고 테이블을 나누는 것은 SRP 가 아니라 **수평 분할**이며,
그것은 설계 원칙이 아니라 성능 기법이다.

### 기각의 결정적 근거 — 이미 기각한 것이 되돌아온다

CONCEPT 4.1 에서 `Category` 를 식별자에서 뺀 이유:

> 키에 넣으면 중복 인코딩이며, 설정 실수로 같은 디렉터리가 두 Category 에 걸릴 경우
> 물리적으로 동일한 파일이 서로 다른 식별자 두 개로 등록되어 중복 방지 규칙이 깨진다.

**테이블을 나누면 테이블 이름이 식별자의 일부가 되어 이것이 그대로 재현된다.**

```
config 오기입으로 같은 경로가 두 섹션에 걸림
  → rinex3_daily_ledger 에 1행, rinex3_hourly_ledger 에 1행
  → 같은 파일이 두 번 전송. PK 가 막지 못함
```

현재 구조에서는 `file_name` 이 전역 PK 라 두 번째 등록이 UPSERT 로 흡수되고,
`verify` 가 파일명의 `_01D_`/`_01H_` 와 config 지정값을 대조해 오기입을 잡아낸다.
**분리하면 이 탐지 장치가 무력화된다.**

### 성능 근거도 없다

```sql
CREATE INDEX idx_common_category_origin ON common_ledger (category, origin, state);
```

**`category` 가 선두 컬럼이다.** B-tree 에서 해당 구간으로 바로 내려간다.

| | B-tree 깊이 |
|---|---|
| 100만 행 단일 테이블 | 약 20단계 |
| 25만 행 × 4 | 약 18단계 |

**2단계 차이.** 마이크로초 단위이고 1시간 주기 프로그램에서 측정도 되지 않는다.
분할은 인덱스를 걸 수 없을 때 쓰는 기법인데 우리는 이미 걸었다.

### 잃는 것

| | 단일 테이블 | 4 테이블 |
|---|---|---|
| `db status` 전체 집계 | `GROUP BY category` | 4-way `UNION ALL` |
| `.rnx`/`.crx.gz` 중복 탐지 | 쿼리 1개 | 4개 또는 UNION |
| 스키마 변경 | 1곳 | **4곳. 하나 빠뜨리면 조용히 어긋남** |
| `put_ledger` | 1개 | 4개 → **총 8테이블** |
| Go 코드 | 쿼리 1벌 | 테이블명 동적 조립 또는 4벌 복사 |

마지막이 특히 문제다. 테이블명을 파라미터로 받으면 SQL 을 문자열로 조립해야 하고,
그러면 `database/sql` 플레이스홀더 검증을 못 쓴다. 4벌 복사하면 DRY 가 깨진다.

### 채택 — 단일 테이블 + `CategoryLedger`

"각 경로가 자기 것만 본다"는 요구는 타당하다.
**저장 구조가 아니라 코드 구조로 달성한다.**

```go
// 하나의 인스턴스는 하나의 Category 만 담당한다.
// 호출자는 category 를 넘길 수 없고, 넘길 필요도 없다.
type CategoryLedger struct {
    db  *sql.DB
    cat domain.Category
}

func (l *CategoryLedger) Candidates(ctx context.Context) ([]Candidate, error) {
    return queryCandidates(ctx, l.db, l.cat)
}
```

- `put` 흐름은 자기 Category 외 데이터에 **접근할 방법 자체가 없다.** 캡슐화로 강제
- 스키마는 한 벌
- FK 와 트랜잭션이 살아 있음
- 테스트에서 4개 인스턴스를 만들어 상호 간섭 없음을 검증 가능

**SRP 는 여기서 충족된다.** `CategoryLedger` 의 변경 이유가 하나,
스키마의 변경 이유도 하나다.

`db.go` 와 `common.go` 는 수정 불필요. `ledger` 패키지에 추가만 한다.

## 8. 첫 실행 폭주 — `seed` 를 원격 나열 기준으로 정의하여 해소

### 문제

로컬 디스크에 10년치가 있고, 빈 장부로 지리원에 붙이면
**Deep Scan 7일치 약 4.2만 개**(3형태면 12.6만)가 한 번에 큐에 들어간다.
기존 송신자가 이미 보낸 것을 통째로 재전송하는 셈이다.

### 기각 — 로컬 기준 `seed`

초안은 "`seed --days N` 이 **현재 로컬 파일**을 `VERIFIED` 로 등록한다"였다.
**기각한다.**

로컬에 존재한다는 것은 보내졌다는 뜻이 아니다.
기존 송신자가 전송에 실패한 파일까지 `VERIFIED` 로 굳으면,

- `revision` 이 오르지 않는다 (파일이 안 바뀌므로)
- 후보 조회에서 영구히 제외된다
- 자동 Scan과 Deep Scan으로는 다시 부를 수 없다 (장부상 이미 성공이므로)

외부에서 누락을 발견해 명시적으로 `resend`하지 않는 한 영구 미전송이 된다.
장부를 도입한 목적 자체를 무너뜨리는 동작이다.

### 채택 — 원격 나열 기준 `seed`

`seed` 는 **전송만 생략한 1회 정상 실행**이다.

```
1) 로컬 스캔 → common_ledger 에 전부 등록 (Ingress 검증 포함)
2) 원격 목적지 디렉터리를 나열
3) 파일별 판정
     원격에 있고 size 일치   → put_ledger 에 VERIFIED 기록
     원격에 없거나 size 불일치 → 아무것도 기록하지 않음
4) 종료. 이후 정기 실행이 3-b 를 정상 후보로 잡아 전송한다
```

**근거 1 — 추정이 아니라 검증이다.**
"원격 존재 + size 대조" 는 설계안 8.1 의 Transfer Verification 과
동일한 기준이다. 전송을 생략했을 뿐 검증 자체는 실제로 수행한다.

**근거 2 — 실패 방향이 안전하다.**
기존 송신자가 다른 원격 구조를 썼거나 RemotePath 가 어긋나면
`seed` 는 아무것도 찾지 못하고 전부 전송 대상이 된다.
**헛전송이지 누락이 아니다.**

**근거 3 — 비용이 낮다.**
파일당 `stat` 이 아니라 **디렉터리당 나열 1회**다.
7일 Hourly 기준 336회이며 일회성 명령이므로 수 분이면 끝난다.

**정기 실행에는 이 확인을 넣지 않는다.**
매시간 원격을 뒤지면 왕복 비용이 상시로 드는데, 전환은 한 번뿐이다.

**구현상 이점** — 원격 나열은 9절의 `DirLister` 를 SFTP 구현으로 갈아끼우면
그대로 재사용된다. `seed` 전용 코드가 거의 필요 없다.

### 남는 한계

같은 이름의 파일이 원격에 있으나 **내용이 다른** 경우는 구분하지 못한다.
size 대조로 대부분 걸러지며, 이는 정상 전송의 Transfer Verification 과
같은 수준의 한계다. 별도 대책을 두지 않는다.

### 함께 두는 것

| | |
|---|---|
| `--dry-run` | 전송 없이 규모만 보고. **가장 먼저 실행** |
| `MaxFilesPerRun` | 실행당 상한. `seed` 를 빠뜨렸을 때의 최후 방어선 |

`--dry-run` 은 현장 접근 불가 상태에서 **현장 조사를 대신한다.**

```
[DRY-RUN] cat=RINEX3_HOURLY dirs=336 files=42000 sites=127
          date-range=2026-08-22 ~ 2026-08-28
          ext: .rnx=42000 .crx=0 .crx.gz=0
[DRY-RUN] cat=RINEX2_HOURLY dirs=336 files=0     ← 환경 이상 의심
[DRY-RUN] 전송 예정 총 84,000 개 / 20.1 GB
```

여기서 추정만 하던 것들이 한 번에 확정된다.

- 관측소 실제 개수 (120 이 맞는지)
- **`.rnx` / `.crx` / `.gz` 중 무엇이 실제로 있는지 → 30일 장부의 실제 용량**
- 경로 템플릿이 맞는지 (`files=0` 이면 틀림)
- 스캔 실소요 시간
- 수신기가 임시명 후 rename 하는지 (3절 미확인 항목)

### 결정 상태

**보류.** `--dry-run` 결과를 본 뒤 `seed` 필요 여부를 판단한다.
`MaxFilesPerRun` 은 어느 쪽이든 최후 방어선으로 넣는 방향.

> **전환 계획** — 이 프로그램이 유일한 송신자가 되는 것이 목표이므로(10.5),
> 첫 붙임은 "추가 투입"이 아니라 **"기존 송신자 대체"**다.
> 따라서 순서가 정해진다.
>
> ```
> --dry-run 으로 규모 확인
>   → 크롤링으로 기존 송신자 종료를 실측 확인 (통보만 믿지 않는다)
>   → seed 로 기존 전송분을 장부에 등록
>   → 정상 가동
> ```
>
> 병행 운영 기간이 있다면 `seed` 시점을 기존 송신자 종료 시점에 맞춰야 한다.

## 9. 확정된 `scan` 패키지 설계

### 위치 — `internal/scan` 으로 분리

GUIDELINES 4절에 `put/` 내부에 둘지 미정으로 남아 있던 항목이다.
DOWNLOAD 도 사용하므로 분리한다.
`put` 과 `download` 는 필요한 인터페이스를 consumer-side 로 선언하고,
`scan` 은 양쪽을 알지 못한다.

### 책임 — 판정하지 않는다

```
scan   → 어떤 파일이 어디에, 크기·시각이 얼마인가   (사실)
verify → 이 파일이 전송 가능한 상태인가            (판정)
ledger → 이미 보냈는가                              (기록)
```

`scan` 은 `ReadDir` 결과를 그대로 올린다.
0바이트도 `.part` 도 거르지 않는다. Grace Time 판정은 `verify` 몫이다.
섞으면 나중에 분리할 수 없다.

### `DirLister` 인터페이스 — 로컬/원격 공용

PUT 의 로컬 스캔과 DOWNLOAD 의 원격 스캔은 **같은 성격의 홉**이다.
`os.ReadDir` 에 직접 붙이지 않는다.

```go
type DirLister interface {
    List(ctx context.Context, dir string) ([]Entry, error)
}

type Entry struct {
    Name  string
    Size  int64
    MTime time.Time
    IsDir bool
}
```

**주된 근거는 테스트다.** fake 하나로 스캔 전체를 검증할 수 있고,
실제 디렉터리도 SFTP 서버도 필요 없다 (GUIDELINES 7절 요구사항).
DOWNLOAD 재사용은 부수 효과다.

> 2026-08-29 — `List` 에 `context.Context` 를 추가했다(구현과 정합).
> 원격(SFTP) 구현에서 취소·타임아웃 전파가 필요하고, 로컬 구현은 무시하면 된다.
> 시그니처에서 ctx 를 빼면 나중에 원격 구현이 들어올 때 인터페이스가 깨진다.

### Hourly의 `(HH)` — 과도기 결정, MVP2에서 교체 (2026-09-15)

**현재 결론:** `HourLayout=dir/flat`은 서울시의 `(HH)` 없는 평면 Hourly
경로를 급히 지원하기 위해 2026-09-04 추가한 과도기 설정이다. 근본 해결은
`HourLayout`과 날짜당 00~23 계산을 제거하고 설정 루트 아래를 범위 제한 재귀
탐색하는 것이다.

**하지 말 것.** Hourly `(HH)` 필수 검증을 재강화하거나 날짜당 00~23 계산을
장기 설계로 되돌리지 않는다. 현재 코드의 `HourLayout`과 `(HH)` 전개는
과도기 동작이며 제거 대상이다.

원격 전송 경로는 로컬 폴더 구조와 분리한다. 로컬 하위 구조를 복제하지 않고
RINEX 버전별 고정 평면 경로(운영 예: `D:\incoming\RNX2`,
`D:\incoming\RNX3`)로 전송하므로 날짜·시각을 이용해 원격 경로를 계산할
필요가 없다.

재귀 탐색의 상세 경계는 아직 확정하지 않는다. 대표가 다음 Linux 설치처에
OS 버전과 실제 경로를 확인한 뒤 재귀 시작점·최대 깊이·날짜 범위 적용 방식·
권한 오류·symbolic link/junction 정책을 정한다.

아래는 2026-08-28 당시 정확한 템플릿 전개를 선택했던 역사 기록이다.

당시 이 문서와 `pathpl` 코드가 서로 다른 방침을 담고 있었다.
`pathpl.HasToken` 주석은 "Hourly 경로에 `(HH)` 가 빠지면 거부하라"고 적었는데,
이 절은 "`(HH)` 를 계산하지 않는다"고 적혀 있었다. 당시에는 코드 쪽으로
통일했지만, 2026-09-15 현재 그 결정은 폐기하고 제한 재귀 탐색으로 교체한다.

**당시 결정은 config.ini의 Hourly `LocalPath` / `RemotePath`에 시각까지 적는 것이었다.**

```
E:\RINEX-V3-H\(YYYY)\(DOY)\(HH)\
```

**근거 — 현장 확인 (운영자)**

> 당시에는 모든 관측소가 시각까지 디렉터리를 두며 지리원도 `(HH)` 폴더가
> 있다고 판단했다. 2026-09-15 재확인 결과 지리원에는 `(HH)` 폴더가 없으므로
> 이 전제는 폐기한다.

12절에서 해당 가설을 기각했던 판단 역시 2026-09-15에 번복한다.
현장 화면 일부만으로 전체 디렉터리 구조를 일반화하면 안 된다는 사례로 남긴다.

**과도기 구현에서는 scan이 시각 24개를 만들어 각각 `ReadDir`한다.**
하위 폴더를 나열해 `^\d{2}$` 로 거르는 방식은 채택하지 않는다.

**부수 근거**

- **당시에는 RemotePath에도 `(HH)`가 필요하다고 가정했다.** 현재 운영 목적지는
  RINEX 버전별 고정 평면 경로이므로 이 근거는 폐기한다.
- **나열 방식은 필터 규칙이 하나 더 필요하다.** 현장 화면에 `00_backup` 같은
  항목이 섞여 있었으므로 예외 관리가 늘어난다.
- `HasToken` 은 이미 구현·테스트가 끝난 검증 장치다. 나열 방식이면 쓸 곳이 없다.

**나열 방식의 원래 근거였던 MVP 2 원격 왕복 절감은 이득이 작다.**

| | 왕복 | RTT 30ms |
|---|---|---|
| **A (7일 × 24 × 2종)** | **336회** | **약 10초** |
| B (7일 × 2종) | 14회 | 약 0.4초 |

1시간 주기에서 10초는 감당된다.

**당시에는 `pathpl`을 수정하지 않고** 다음 두 곳을 확정했다.

| | 내용 |
|---|---|
| config 검증 | `cat.IsHourly()` 면 `tpl.HasToken(pathpl.TokenHH)` 를 요구한다. 없으면 시작 시 거부 |
| config 검증 | Daily 경로에 `(HH)` 가 있으면 거부한다. 시간 단위 디렉터리가 존재하지 않기 때문 |
| scan 루프 | 날짜당 시각 0~23 을 만들어 각각 `Expand` → `ReadDir` |

> **scan 구현 주의** — 05시 디렉터리가 없으면 `os.ReadDir` 이 `ENOENT` 를 낸다.
> **오류가 아니라 정상이다.**
> 크롤링 매트릭스에서 시간 슬롯의 22% 가 비어 있음이 확인되었다(10.3).
> `errors.Is(err, fs.ErrNotExist)` 면 조용히 건너뛰고 그 외 오류만 기록한다.
> 이것을 오류로 취급하면 정상 운영에서 매시간 수백 건의 오류 로그가 쌓여
> 진짜 오류가 묻힌다.

> `SFTPClient_PROJECT_GUIDELINES.md` 9.3은 2026-09-15 현재 결론으로 갱신했다.

7일 × 3형태면 12.6만 건이다. 슬라이스에 전부 담으면 수십 MB 가 메모리에 뜬다.

## 10. 확인 항목 — 답변 (2026-08-28, 지리원 기준. 측위원도 유사)

> 전제 — 이 데이터는 국가기관이 관리하는 측량 자료이며,
> 본 프로그램은 **그것을 전송하는 역할만** 한다.

### 1. 수신기가 임시명 후 rename 하는가 — 해당 없음

수신기 내부에서는 `.t04` 로 저장하고 전송하나, 그 뒤 QC 처리를 거쳐 완제품이 저장된다.
**우리가 다루는 것은 QC 를 모두 마친 압축 완제품이다.**

→ **append 성장이 존재하지 않는다.** 크기가 변하는 구간은 전송 중뿐이며 수 초~수 분이다.
→ `GraceSeconds = 60` 확정. CONCEPT 4.4 의 "쓰기 사이 공백의 최대치를 알 수 없다"는
   서술은 우리 서버에 적용되지 않으므로 갱신 대상이다.

**확장자 목록은 불필요하다.** 실제 압축 형식은 `.gz` / `.Z` / `.zip` 등 다양하나,
정규화 규칙이 "압축 확장자를 **보존**한다"이지 "인식한다"가 아니므로
`.part` 만 제거하고 나머지는 문자열 그대로 둔다. 알려진 목록을 유지할 필요가 없고,
새로운 압축 형식이 등장해도 코드를 수정하지 않는다.

식별은 파일명에 이미 포함된 관측소명 + 연도 + DOY 가 담당한다.
`.crx.gz` 와 `.crx.Z` 는 서로 다른 파일명이므로 다른 행이 되고 각각 전송된다.
확장자 필터를 두지 않기로 한 결정과 일관된다.

> **사소한 주의** — `.Z` 는 소문자화되어 `.z` 가 된다.
> 같은 디렉터리에 `foo.Z` 와 `foo.z` 가 공존하면 식별자가 충돌한다.
> 실무에서 발생할 가능성은 없다고 판단하나 기록해 둔다.

### 2. 확장자 — 3형태 모두 존재. 항법자료 포함

측위원은 항법 자료까지 취급하므로 `.rnx` / `.crx` / `.crx.gz` 가 모두 존재한다.

**용량 재계산** (`local_path` 삭제분 + 크롤링 실측 반영)

기존 추정은 "120개 관측소 × 24시간이 전부 채워짐"을 가정했으나,
크롤링 매트릭스 확인 결과 **국토지리정보원은 109개 관측소이며
시간단위 도착률이 78.4%, 일단위 68.1%** 다. 과대추정이었다.

| | 하루 파일 수 |
|---|---|
| 1형태 | 약 4,250 |
| **3형태** | **약 12,700** |

| 30일 | 행 수 | 용량 |
|---|---|---|
| 1형태 | 약 13만 | 약 65MB |
| **3형태** | **약 38만** | **약 200~225MB** |

항법자료가 더해지면 상승하나 여유가 있다.
`DELETE` 로는 파일이 줄지 않으므로 해당 지점에서 평형을 이룬다.

**주의 — 항법 파일은 필드 구성이 다르다.**

```
관측  SONP00KOR_R_20260010200_01H_01S_MO.crx.gz    ← 데이터율 필드 있음
항법  SONP00KOR_R_20260010000_01D_MN.rnx           ← 없음
```

`_01D_` / `_01H_` 대조는 그대로 동작하나,
**고정 오프셋으로 자르는 코드는 항법 파일에서 어긋난다.**
결측 리포트용으로 검토했던 `substr(file_name, 25, 2)` 방식이 여기 걸린다.
위치가 아니라 `_` 분리 후 필드 검사로 구현해야 한다.

### 4. 경로 템플릿 정확성 — 2026-09-15 재검토

설치자가 본인 또는 자사 직원으로 한정된다. **휴먼에러를 가정하는 것은 과설계다.**
경로 오타 검증에 코드를 쓰지 않는다.

단, `files=0` 경고는 유지한다. 이는 사람의 실수가 아니라
**환경 이상(마운트 해제, 권한 변경, 드라이브 미인식)**을 잡는다.
로그 한 줄이므로 비용이 없다.

위 결론은 "정확한 경로 모양을 이미 안다"는 전제에서 나온 것이다. 이후 서울시
평면 Hourly와 지리원의 `(HH)` 없는 경로가 확인되었고, Linux 설치처의 구조도
확인 전이다. 따라서 개별 템플릿 오타를 추측해 교정하지 않는 원칙은 유지하되,
템플릿이 모든 기관 구조를 표현할 수 있다는 전제는 폐기한다. MVP2에서는 설정
루트 아래의 범위 제한 재귀 탐색으로 구조 차이를 흡수한다.

### 5. 다른 프로그램이 전송 중인가 — 전환기 한정 위험

기관마다 다르다. 지리원·측위원은 멈추었다고 통보받았으나
크롤링하면 데이터가 들어온다. 현재 정체 불명의 송신자가 존재한다.

**다만 이는 항구적 상태가 아니라 전환기 상태다.**

> 이 프로그램이 완성되면 파일을 전송하는 프로그램은 이것이 유일해진다.
> **난잡하게 흩어진 여러 프로그램을 하나로 통일하는 것이 개발 목적 중 하나다.**

따라서 문제는 "다른 송신자와 영구히 공존하는 설계"가 아니라
**"기존 송신자를 끄고 이것으로 넘어가는 절차"**다. 설계가 아니라 전환 계획의 문제다.

**전환기에 필요한 것**

| | |
|---|---|
| `--dry-run` | 붙기 전 규모 확인. 크롤링 결과와 대조해 겹침 파악 |
| `seed --days N` | **원격 목적지를 나열하여, 이미 도착해 있는 파일만** `VERIFIED` 로 등록 (8절) |
| 기존 송신자 종료 확인 | 통보가 아니라 **크롤링으로 실측 확인**. 이미 통보와 실제가 어긋난 전례가 있다 |

전환 순서는 `--dry-run` → 기존 송신자 종료 확인 → `seed` → 정상 가동이다.

### 파생 결과 — 장부의 위상이 올라간다

통일 이후에는 우리 프로그램이 유일한 송신자이므로,
**장부가 "우리가 보낸 것"이 아니라 "보내진 것 전체"의 기록이 된다.**

| | 장부가 답할 수 있는 것 |
|---|---|
| 전환 전 | 우리가 무엇을 보냈는가 |
| **통일 후** | **무엇이 보내졌는가 / 무엇이 안 보내졌는가** |

이는 다음 두 가지를 가능하게 한다.

- **수신측과의 대조가 성립한다.** 차이가 나면 그것은 실제 누락이지
  "다른 송신자가 보냈나?"라는 불확실성이 아니다.
- **결측 리포트(1절 C)의 신뢰도가 올라간다.**
  크롤링 엑셀(3절)과 장부를 대조할 때, 장부에 없는 것은 정말로 안 나간 것이다.

설계에 변경은 없다. 장부라는 선택이 통일이라는 목적과 정합한다는 근거가 하나 늘어난 것이다.

### 6. `local_path` — 스키마에서 제거 (6절 참조)

### 7. 스토리지 — **SMB 확정**. 그리고 요구가 바뀌었다

현장 화면에서 확인되었다.

```
X:  →  \\192.168.103.100\gnss-prod-nas\data
```

**SAN 이 아니라 SMB(NAS) 다.** 며칠간 추측만 하던 항목이 닫혔다.
같은 화면에서 `2016` ~ `2026` 폴더가 확인되어 **로컬 보존이 10년**임도 확정되었다.

Windows 에서는 `ReadDir` 이 크기·시각을 함께 반환하므로 디렉터리당 왕복이
1~2회이고 파일당 왕복이 아니다. 현 단계에서 문제되지 않는다.
**Linux 확장(MVP2) 시에는 파일당 `lstat`이 발생하므로 재검토가 필요하며,
계측 로그에 이 구간을 분리해 두는 것이 그때 근거가 된다.**

> 대표 요구는 **어떠한 환경에서도 동작하는 것**이다.

이에 따라 **Windows 전용 수단을 주된 판정 수단으로 삼을 수 없다.**

```
주    mtime + GraceSeconds     ← 어디서나 동작. 이것만으로 성립해야 한다
보조  파일 잠금 검사            ← Windows 한정. 있으면 더 정확
최후  revision                  ← 어디서나
```

**보존 10년 vs 장부 30일** — 이 격차가 `LedgerRetentionDays > ScanDays` 조건을
절대 조건으로 만든다. 장부에서만 지워진 파일이 Scan 범위에 들어오면
전량 재전송된다. config 검증에서 강제한다.

### 8. 측위원 중간서버 설치 — 가능

→ **현재 알려진 모든 기관에 DOWNLOAD 가 불필요하다.**

```
[서버 A] --PUT--> [중간서버 B] --PUT--> [최종 C]
```

DOWNLOAD 는 "타 기관 소유라 설치가 불가한 서버"가 나타날 때를 위한 빈 칸이다.
구조물은 유지하되 구현은 MVP3으로 연기한다.

### 9. 수신기 60분 설정 vs 3~4시간 지연

수신기 설정은 서울시 방문 시 확인한 것이고,
3~4시간 지연은 크롤링을 통해 관찰한 것이다. 서로 다른 관측이다.

→ `ScanRecentDays = 2` 는 어느 쪽이든 충분히 덮으므로 현 시점에 조치 불요.

→ 같은 실측이 `LockStaleSeconds = 10800`(3시간)의 근거이기도 하다 (14절).
  지연분이 한 회차에 몰리면 버스트가 되어 최장 실행이 길어지므로,
  stale 문턱은 그 상한을 덮어야 한다.

비용은 문자열 비교 하나이며, 원인 불명의 혼입이 실제로 관측된 이상

## 14. `LockStaleSeconds` — 단위·기본값·validate 확정 (2026-08-30)

> 대상은 `internal/config` 과 `config.example.ini` 이다.
> `internal/lock` 패키지는 config 를 import 하지 않는다.
> 경로·staleAfter 는 인자로 받으며, main 배선은 put 조립 단계에서 한다.

### 제기된 의문

stale 문턱을 ini 에 둘 때 **초(`LockStaleSeconds`)인가 분(`LockStaleMinutes`)인가.**
기본값은 얼마인가. validate 하한·상한은 무엇인가.

### 채택 — `LockStaleSeconds` (초)

config.ini 키는 `LockStaleSeconds`, 내부 필드는 `General.LockStale time.Duration`.
`GraceSeconds` → `Ingress.Grace` 와 같은 방침이다.
초 단위 int 를 그대로 두면 사용처마다 `time.Second` 곱셈이 반복되고 한 곳은 빠뜨린다.

### 기각 — `LockStaleMinutes`

Minutes 안의 이득은 두 가지였다.

| # | Minutes 안의 이득 | 대체 수단 |
|---|---|---|
| ① | ini 에서 `180` 이 3시간임이 바로 읽힌다 | example.ini 환산 주석 한 줄 |
| ② | GraceSeconds 감각으로 작은 값을 넣는 오입력이 안전한 방향(분)으로 틀린다 | validate 하한 **600초** |

반면 Seconds 의 이득 — **경과시간 키의 단위 규약을 GraceSeconds 와 초 하나로 유지** — 은
Minutes 로는 대체할 수 없다.
대체 가능한 이득과 불가능한 이득이 붙으면 후자가 이긴다.

참고 — `ScanRecentDays`·`DeepScanHour` 는 **달력 좌표**이고,
이 키와 `GraceSeconds` 는 **경과시간**이다. 계열이 다르므로
"키마다 단위가 제각각" 반례가 아니다.

### 기본값 10800 (180분 = 3시간)

근거는 추정이 아니라 **크롤링 지연 실측**이다 (10.9).
크롤링 데이터가 최대 3시간 지연 도착하는 경우가 실재한다(특히 22–23시 데이터).
지연분이 한 회차에 몰리면 버스트 회차가 되어 최장 실행이 길어지므로
그 상한을 덮는다.

| 너무 짧으면 | 너무 길면 |
|---|---|
| 살아 있는 장기 실행의 lock 을 탈취 → **이중 전송 (비가역)** | 크래시 후 그 시간 동안 매시 실행 거부 → 전송 공백 (다음 정상 회차가 디스크−Ledger 로 복구) |

### validate 범위

| 끝 | 값 | 막는 사고 |
|---|---|---|
| 하한 | **600초 (10분)** | GraceSeconds 감각으로 `60` 같은 초급 값을 넣는 오입력. 통과되면 1분 넘는 정상 실행이 탈취 대상 → lock 없는 것보다 나쁨 |
| 상한 | **86400초 (24시간)** | `180` 을 `18000` 으로 적는 부류의 오타. 크래시 후 며칠씩 오류 없이 전송이 멈추는 "오류 없이 잘못 도는" 부류 |

### 구현 위치 (config 5곳 한 세트)

| # | 파일 | 내용 |
|---|---|---|
| 1 | `internal/config/config.go` | `GeneralConfig.LockStale time.Duration` + 단위 결정 주석 |
| 2 | `internal/config/load.go` | `durationSeconds(..., "LockStaleSeconds")` + `knownKeys` |
| 3 | `internal/config/validate.go` | 600초~24시간 |
| 4 | `config.example.ini` | `LockStaleSeconds = 10800` + 운영 주석 |
| 5 | config 테스트 | 픽스처·경계값·키 매핑. example.ini 대조는 4번으로 자동 통과 |

**하지 않는 것** — lock 패키지가 config 를 import 하지 않는다.
`LockStaleMinutes` 키를 만들지 않는다. scan / verify / ledger / pathpl 은 건드리지 않는다.

### main 배선 (2026-08-30 완료)

`cmd/rinexclient` 은 `lock.Acquire(LedgerPath+".lock", LockStale)` /
`Release` 를 호출한다. `ErrHeld` 는 exit 0.
이 절의 “후속” 표기는 폐기한다.
