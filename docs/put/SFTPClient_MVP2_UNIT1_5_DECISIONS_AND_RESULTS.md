명확하고 작은 변경이어서 스톨 설계보다 먼저 처리했다.

## 2. 문제 해석에서 확정한 경계

- 프로세스를 의도적으로 정지한 뒤 남은 `.part`는 통신 스톨의 증거가 아니다.
  다음 시작의 Recover가 처리할 수 있는 중단 잔여물이다.
- QC 오류는 동료 프로그램 쪽 문제였다는 최신 사용자 전달을 반영한다.
  송신 중복이 QC 장애를 일으켰다는 과거 인과 가설을 확정 사실로 쓰지 않는다.
- mtime만 달라 동일 내용이 새 revision으로 취급될 수 있는 코드 경로와,
  현장에서 실제 중복 전송·QC 격리가 얼마나 발생했는지는 별개다.
- 유닛 3은 원격 무응답 가능성에 대한 예방이다. 방화벽 원인 진단이나
  BNC 수신 공백의 해결을 보장하지 않는다.
- “5000파일/45분”은 전체 처리량이다. 개별 파일 시간, 모든 회차의 성능,
  timeout 최적값을 증명하지 않는다.

## 3. 유닛 1 — 실행 로그 보존

### 결정과 이유

표준 `log`를 유지하고 `internal/logging.RotatingWriter`로 출력 대상을
확장했다. main에서 stderr와 파일에 병행 기록한다. slog·호출부 전면 교체·
새 수준 필터 체계는 도입하지 않았다. 전송 코드가 로깅 저장 방식에 의존하지 않는다.

로컬 날짜의 `rinexclient_YYYYMMDD.log`에 append하고, 자정 이후 첫 Write에서
새 파일로 전환한다. 삭제 기준은 파일명 날짜이며 자기 패턴에 맞는 파일만
보존 정책에 따라 정리한다. 프로세스 내부 동시 쓰기는 mutex로 직렬화한다.

파일 기록 장애는 경고 후 전송을 계속한다. 사용자 공간 버퍼를 두지 않되
매 줄 fsync는 하지 않으므로 전원 단절 시 디스크 영속성을 보장하지 않는다.

### 구현 결과와 초안 정정

- 구현: `internal/logging/logging.go`, main의 `log.SetOutput` 배선.
- 실제 설정은 **기존 `[LOG] Dir`, `RetentionDays`**다. 예제 보존값은 30일이며
  Ledger 보존과 책임이 다르다. 유닛 1 초안의 `[GENERAL] LogDir /
  LogRetentionDays` 신설안은 현재 설정 계약이 아니다.
- 상대 경로는 config 로더의 기존 해석 규칙을 따른다. 설정 읽기 이전의
  오류까지 이 파일 로그에 보존된다고 보장하지 않는다.
- 파일 열기·회전·보존 삭제·쓰기 실패 강등·동시 기록의 테스트가 있다.

## 4. 유닛 2 — 내용 지문으로 mtime 변화 구분

### 결정과 결과

전송할 로컬 파일 전체 바이트의 SHA-256을 기준 지문으로 저장한다.
압축 파일이면 압축된 바이트 그대로이며, 압축 해제·업무 내용 해석은 하지 않는다.

- size·mtime 모두 같음: 기존 Unchanged 처리. 매 회차 전량 해시하지 않는다.
- size 같음·mtime 다름·기존 지문과 새 안정 지문 같음: revision을 유지하고
  장부 mtime 기준선만 옮긴다(`MetadataOnly`).
- size 다름 또는 비교 지문 다름: 변경으로 분류해 새 revision을 만든다.
- 기준 지문이 없는 mtime 변화: 동일 내용으로 단정하지 않고 보수 변경 처리한다.
- 해시 관측이 불안정하면 파일을 이번 회차에서 보류한다. 해시 읽기 실패는
  WARN 후 지문 없이 기존 신규/변경·후보 처리를 이어가는 보수 정책이다.

**MetadataOnly와 Unchanged는 전송 완료 상태가 아니다.** 현재 revision의
이력 없음·PENDING·재시도 가능한 FAILED는 기존 후보 경로를 따른다.
mtime만 바뀌었다는 이유로 새 revision을 만들지 않는 것이 핵심이다.

### 장부·백필·모드 계약

- schema v6의 `content_hash`는 최근 안정 관측의 지문이지 원격 전송 완료 증거가 아니다.
  전송 완료는 기존 put_ledger VERIFIED가 소유한다.
- v5→v6, v4→v5→v6 마이그레이션을 지원한다. DB 삭제·재생성으로 대체하지 않는다.
- Touch/SetContentHash는 판정에 사용한 revision·size·mtime·지문 등을 가드한다.
  0행이면 WARN 후 해당 파일을 보류하고, SQL·context 오류는 실제 오류로 반환한다.
- 판정·후보 필수 해시는 제한하지 않는다. Unchanged VERIFIED의 빈 지문을
  채우는 자연 백필만 `[PUT] MaxHashBackfillPerRun` 예산을 적용한다.
- 키 부재=500, 명시적 0=백필 끔, 양수=상한, 음수=설정 오류다.
  백필 시도는 실패해도 예산을 소비한다.
- dry-run은 필요한 판정 해시만 수행하고 장부를 쓰지 않는다. seed는 지문 계산·
  저장을 생략한다. DOWNLOAD origin 제외와 세트 게이트의 기존 의미를 유지한다.

배포 직후 빈 지문 행은 자연 백필 전 mtime이 달라지면 보수 재전송될 수 있다.
즉시 모든 과거 파일의 억제가 완성된다고 약속하지 않는다. size와 mtime을
모두 보존한 내용 변경이나 원격 내용 해시 검증은 이 기능의 보장 범위가 아니다.

## 5. 유닛 5 — 미완성 입력 제외

`IsPartFile`은 대소문자를 무시하고 이름 끝의 `.part`·`.filepart`를 제외한다.
크기·mtime·장부 등록 여부와 관계없이 스캔 후보에서 뺀다. 입력 파일 삭제·
이름 변경·내용 수정·신규 장부 등록은 하지 않으며 기존 집계는 유지한다.

최종 이름이 관측되면 기존 Ingress·해시·변경 판정·세트 조건을 거친다.
rename 사건을 추적하거나 옆 `.filepart`의 소멸을 요구하지 않는다.
최종 이름만으로 파일 내용의 완전성을 보증하지 않는다.

- `NormalizeName`은 계속 `.part`만 제거한다. `FILENAME_V1`은 유지하며
  이 유닛으로 식별자 마이그레이션을 추가하지 않는다.
- `.filepart`는 정규화 불변이므로 장부 이름 가드가 대신 차단하지 않는다.
  미래의 스캔 우회 쓰기 경로도 입력 게이트 계약을 지켜야 한다.
- 자체 업로드의 `.part` 생성·검증·rename 프로토콜은 유지한다.
- 기존 `.filepart` 장부·원격은 별도 청소하지 않는다. 시작 Recover의
  IN_PROGRESS 정리와 FAILED 전이는 기존 정상 동작으로 유지한다.
- `.part`·`.filepart` 집계는 합산한다. 이름 중간의 `.filepart` 및 알 수 없는
  상류 임시 이름은 추가 규칙 없이 차단한다고 주장하지 않는다.

임시 이름 다음 회차의 최종 후보 선정, 기존 PENDING `.filepart` 재선정 차단,
정규화·장부 가드 비대칭이 테스트로 고정되어 있다.

## 6. 유닛 3 — SFTP 무진행 감지와 종료

### 최종 구현

단일 공유 SSH/SFTP 연결을 유지한다. 연결의 진행 중 작업 수와 마지막 진전을
관측하고 **진행 중 작업이 있으며 무진행 시간이 문턱을 넘을 때** 종료를 시작한다.
파일 총 전송 시간이나 연결 idle 시간 제한이 아니다.

- `[PUT.SFTP] StallTimeoutSeconds`: 기본·현재 운영 선택값 **30초**, 허용 5~600.
  앞선 60초 논의는 최종 30초 결정으로 대체됐다. 현장 검증된 최적값은 아니다.
- 계측은 mutex와 monotonic `time.Time`을 사용한다. 유휴 0→1에서 기준을
  새로 잡고 완료·청크 쓰기 성공으로 갱신한다. 진행 중 새 착수만으로 연장하지 않는다.
- 접속은 TCP~SSH handshake~SFTP NewClient~rename 탐침을 단일 10초 예산으로
  보호한다. deadline은 탐침 후 해제한다. 그 이후 Recover·seed·전송은 감시 대상이다.
- 발화 시 표식·로그 → 회차 취소로 신규 착수 중단 → SSH Abort → 기존 실패 처리
  → 함수 반환과 lock 해제 순서다. 스톨 회차는 비정상 종료로 보고한다.
- 일반 취소도 SSH를 닫고 감시자 종료를 기다린다. 이 배선을 단순
  `go WatchStall` 호출로 되돌리면 취소 후 원격 대기가 남을 수 있다.
- Abort는 멱등이며 이후 Close는 SFTP 종료 대기를 다시 하지 않는다.

### 유지한 정책과 한계

취소와 분리된 짧은 context로 실패 기록을 시도한다. 남은 IN_PROGRESS는
다음 시작 Recover가 회수한다. Recover도 원격 오류가 계속되면 완료되지
않을 수 있으므로 다음 회차 성공을 보장하지 않는다.

통신 실패는 common revision 사건이 아니다. BeginPut의 attempts 소비와
MaxRetries 상한을 유지한다. 자동 재시도는 스캔 범위·남은 예산 안에서만
가능하다. 무제한 재시도·예산 환급·회차 내 재연결은 추가하지 않았다.

다른 워커의 진전이 한 워커의 멈춤 감지를 늦출 수 있다. 로컬/NAS 읽기는
SSH를 닫아도 풀리지 않으며 회차 전체 상한·강제 종료는 이번 범위 밖이다.
lock은 하트비트/PID 생존이 아니라 나이 기반이라, 오래 실행한 회차는
30초 감지 전에도 stale 탈취될 수 있다. 조기 종료는 이중 실행 위험을
줄일 뿐 제거를 보장하지 않는다. 600초 허용 상한 역시 그 보장이 아니다.

keepalive·워커별 연결·이어받기·방화벽 원인 판별은 도입하지 않았다.
실제 DROP/RST와 SFTPGo에서의 종료·lock 해제·재실행 성공은 별도 미검증이다.

## 7. 유닛 4 — 기존 회차 요약 확장

새 경보 시스템 대신 기존 `RunReport.Print`에 아래를 추가했다.

- `evaluated = Unchanged + New + Changed + MetadataOnly`.
- `suppressed_ratio = MetadataOnly / evaluated`의 백분율. 분모 0은 `n/a`.
- `mode=live/dryrun/seed`, `range=hot/deep`. 범위 미설정은 `unset`.
  seed는 전체 ScanDays 창이므로 deep으로 표시하고 mode로 구분한다.

분모는 전송 후보나 MaxFilesPerRun 절단 결과가 아니다. 파일-회차의 기존
분류 카운터 합을 출력 시 계산하며 별도 증가 카운터를 추가하지 않는다.
카테고리별 집계에 붙여 기존 로그와 중복되는 DRIFT 줄을 만들지 않았다.

해석상 주의:

- `metadata_only`는 개념상 mtime_drift_suppressed이며 이상 확정 건수가 아니다.
- `changed`에는 지문 미확보·해시 실패의 보수 변경도 있어 실제 내용 변경
  확인 건수라고 단정하지 않는다.
- 분모 0은 판정 집계가 없다는 뜻이지 “스캔 파일이 0개”라는 뜻은 아니다.
  listed·거부·오류 집계를 함께 본다.
- 카운터는 분류 시점의 사실이다. MetadataOnly 이후 Touch 가드 0행,
  Unchanged 분류 이후 필수/백필 해시 불안정으로 보류된 파일도 있을 수 있다.
  따라서 evaluated를 최종 처리 성공 수로 보거나 모든 HashUnstable을
  무조건 분모 밖이라고 해석하지 않는다. 판정·전송 순서는 변경하지 않았다.
- 요약은 스캔·후보 단계 결과이며 이후 전송 성공을 보증하지 않는다.
  중도 오류로 요약이 없으면 0건으로 해석하지 않는다.

suppressed·changed의 임계 경보는 **필수가 아니다**. 400 등 근거 없는 값을
넣지 않으며, 실측 후에도 운영 조치에 도움이 없으면 도입하지 않는다.
정상 분포·쌍봉 가설·기관별 예상치는 측정 전 가설로 남긴다.

exhausted>0은 자동 재시도 탈락 신호이므로 기존 WARN과 최대 5개 예시를
유지하고 회귀 테스트로 확인한다. 이는 이번 스캔에서 본 제외 건수이며
DB 전체 미전송 잔량은 아니다. 경고와 운영자 재개는 별개다.

연속 STALL, lock 장기 점유, 임시 파일 장기 잔류 경보 및 외부 알림,
회차 간 상태 저장은 추가하지 않았다.

## 8. 검증 결과의 범위

- 유닛 2 문서는 2026-09-18 전체 테스트 통과와 마이그레이션·가드·해시
  회귀 검증을 기록한다. 후속 계획은 사용자 환경 race 통과 전달을 기록한다.
- 유닛 5 문서는 전체 테스트 통과와 임시 파일 제외 계약 검증을 기록한다.
- 이 대화의 유닛 3 보완 시 전체 테스트·vet·빌드 통과가 확인됐다.
- 유닛 4 리뷰 및 취소 배선 복원 시 PUT·transport·main 관련 테스트와
  빌드 통과가 확인됐다. 이후 사용자 최종 수정본에 대해 이번 문서 작업에서
  테스트를 새로 실행한 것은 아니다.
- 테스트 존재·과거 통과와 최신 배포 바이너리의 현장 검증은 구분한다.
  DROP/RST, Linux 실제 경로·스케줄러, 기관별 SFTP 환경 검증 완료를 주장하지 않는다.

## 9. 남은 작업과 운영 확인

1. 배포본과 DB 백업을 확보하고 기존 DB의 v5→v6 전환·데이터 보존을 확인한다.
2. 파일 로그 생성·보존·실행 시간과 기관별 mode/range 집계를 확인한다.
   로깅 보존 구현과 Ledger Retention 구현 완료를 혼동하지 않는다.
3. SFTP 무응답 시 실제 종료, lock 해제, 통신 회복 후 재시도를 확인한다.
   소진·스캔 범위 이탈은 별도로 확인한다.
4. 기존 `.filepart` 장부·원격 흔적과 상류 임시 이름 방식을 확인한다.
   삭제·원격 청소는 이 묶음의 자동 동작으로 추가하지 않는다.
5. suppressed 추이를 기관·모드·스캔 창별로 관측한다. 임계 경보는 필요할 때만
   별도 결정하며, exhausted·STALL·전송 오류 신호는 유지한다.
6. resend 의미론, 경로 범용화, Linux 배포, Ledger Retention 등 기존 MVP2
   잔여 작업은 가이드라인의 별도 범위를 따른다. 이 문서로 완료 선언하지 않는다.

이 종합본 작성에서는 운영 설정·코드·DB·원격 파일을 변경하지 않았다.
