## 1. 인시던트 문서 ↔ HEAD 소스 대조 결과 `[확정]`

| # | 인시던트 주장 | 코드 실물 | 판정 |
|---|---|---|---|
| 1 | unchanged 판정 = `size == && mtime ==` (runner.go) | `exists && k.Size == e.Size && k.MTime == mtime` 그대로. 카테고리 무관 동일 적용 | 일치. 코드는 설계대로 동작, 버그 아님 |
| 2 | `internal/logging` 부재, 표준 `log` → stderr 전용 | 패키지 없음. `cmd/rinexclient/main.go` 표준 `log`만 사용 | 일치 |
| 3 | `.filepart` 미인식 | `domain/filename.go` `partSuffix = ".part"` 단일 상수 | 일치 |
| 4 | 해시 판정에 스키마 변경 필요 | schema v5에 `content_hash` 없음 → v6 마이그레이션 선결 | 일치 |

### 1.1 코드 대조로 새로 확인된 사실 — RNX3 hung 메커니즘 `[확정]`

`transport/sftpfs.go`:

- `dialTimeout`(10s)은 TCP 연결 + SSH handshake까지만 적용. handshake 직후
  `SetDeadline(time.Time{})`으로 데드라인 **해제**.
- SSH keepalive 없음.
- `UploadPart`는 청크 **사이**에서만 ctx 확인 → 진행 중인 SFTP Write 하나가
  네트워크 스톨로 블록되면 해당 고루틴 무한 대기.
- `main.go`는 `signal.NotifyContext`뿐, 실행 전체 watchdog 없음.

→ "0바이트 `.part` 25분 잔류"는 이 조합으로 재현 가능한 현상이다. 전송 미완료
→ VERIFIED 전이 불가 → 그 사이 mtime 폭풍이 revision을 올려 rev≈24 누적
(산술 정합).

### 1.2 연결 공유 구조 `[확정]`

`main.go`는 `DialSFTP` 1회로 만든 단일 `SFTPFS`(ssh.Client 1 + sftp.Client 1)를
Uploader로 전달하고, MaxWorkers개 워커가 이를 **공유**한다.
→ 연결 데드라인은 연결 전체에 걸리고, watchdog이 연결을 닫으면 모든 워커가
동반 실패한다. 유닛 2 정책 결정의 전제 사실.

## 2. 교차검증(GPT) 4개 지적 — 검수 판정

**총평: 4개 모두 타당, 수용.** 아래 보완 사항과 함께 각 유닛 설계에 반영한다.

### 2.1 "이전 해시 확보" — 수용 (설계 빈틈이었음)

"애매할 때만 해시"는 비교할 기준 지문이 있어야 성립한다. 확정 흐름:

- **신규 파일:** 최초 등록 시 해시 저장.
- **실제 변경(새 revision):** 새 revision의 해시 저장.
- **기존 v5 행의 자연 백필:** `size= · mtime=`(unchanged 판정 통과) 시 해시를
  계산해 저장. 안전 근거 — "size=·mtime=이면 내용 동일"은 현행 unchanged
  판정이 이미 서 있는 신뢰 기반이므로 **새 가정을 도입하지 않는다**.
- **해시 없는 행이 mtime 드리프트를 먼저 만난 경우:** 판별 근거가 없으므로
  1회 보수적으로 새 revision 처리(전송) + 지문 기록. 이후부터 방어 작동.
  (백필 과거분을 조용히 누락시키지 않는 보수적 선택 — 누락 > 헛전송)

**보완(검수자 추가): 백필 상각.** 측위원 common_ledger 11만 행 이상 — 첫 실행
전량 백필은 수십 GB 로컬 읽기가 한 회차에 몰린다. **`MaxHashBackfillPerRun`
상한으로 회차 분할 상각**한다. 상한 기본값과 근거는 유닛 3 설계문에서 확정.

### 2.2 `MetadataChangedOnly` + mtime 갱신 — 수용

해시 같고 mtime만 다른 경우 장부 mtime을 현재 값으로 갱신하지 않으면
**같은 파일을 매 실행 반복 해시**한다. 판정 결과를 3분화:

| 결과 | revision | state | mtime | 후보 | 관측 |
|---|---|---|---|---|---|
| `Unchanged` | 유지 | 유지 | 유지 | 아니오 | unchanged 집계 |
| `ContentChanged` | +1 | CHANGED | 갱신 | 예 | changed 집계 |
| `MetadataChangedOnly` | 유지 | **유지** | **갱신** | **아니오** | 별도 집계(§2.3) |

**보완(검수자 추가) 2건 — 유닛 3 설계문 필수 기록 사항:**

1. **mtime 컬럼의 의미 재정의.** "마지막 전송 시점의 관측 사실" →
   "**변경 판정 기준선**"으로 주인이 바뀐다. "하나의 사실에 하나의 주인"
   원칙상 스키마 주석과 LEDGER_CONCEPT에 명문화하여 재론을 막는다.
2. **DOWNLOAD-origin 분기 적용 여부.** `runner.go`의 DOWNLOAD-origin 제외
   분기도 동일한 `k.MTime == mtime` 비교를 쓴다. metadata-only 갱신을 이
   분기에 적용하지 않으면 origin=DOWNLOAD 파일이 mtime 드리프트 시 매 회차
   재검증된다. 적용 여부와 근거를 유닛 3 설계 범위에 포함한다.

### 2.3 경보 이원화 — 수용

해시 방어 적용 후 mtime 폭풍은 CHANGED가 아니라 `MetadataChangedOnly`로
흡수되므로, CHANGED 폭주 경보만으로는 상류 이상을 볼 수 없다.

- **`content_changed` 폭주** — 실제 내용 변경 대량 발생.
- **`mtime_drift_suppressed` 폭주** — 내용 동일·mtime 대량 변경, 재전송 억제.
  → "전송 피해는 막았으나 상류에서 잘못된 복사 작업 발생"의 관측 신호.
  방어가 장애 흔적까지 숨기지 않는다.

### 2.4 스톨 방어 정책 선결 — 수용 (전제 사실 §1.2로 확인)

"deadline + keepalive + watchdog" 단어만으로 구현하지 않는다. 유닛 2 설계문에서
다음을 먼저 확정한다:

1. 스톨 시 실행 전체 실패 후 다음 스케줄 재시도 vs 부분 계속
2. 워커별 독립 SFTP 연결 vs 공유 연결 유지
3. 공유 유지 시 연결 단위 watchdog의 폐기 범위(동반 실패 허용 여부)
4. SSH keepalive 실패 횟수와 작업 타임아웃의 구분
5. 연결 강제 종료 후 IN_PROGRESS → FAILED 확정 절차

**제약(검수자 추가):** 설계안 12.3이 "연결 방식(단일 연결 다중 세션 vs 워커별
연결)은 MVP4 벤치마크 후 확정"으로 미뤄둔 항목과 겹친다. 유닛 2의 결정은
MVP4 측정과 충돌하지 않는 **안전장치 범위로 한정**한다 — 성능 선택을
선점하지 않는다.

| 순서 | 유닛 | 내용 | 핵심 확정 사항 |

- "중복/재도착 파일이 QC 오류를 일으킨다"는 논리(가설 4, H1 계열)는
  **무력화**된다. 시간 파일도 재전송 폭풍을 동일하게 맞았는데 정상이라면,

  Daily 대용량 파일에서 스톨 발생 가능성이 Hourly보다 높음: §1.1 메커니즘과
  정합)과 가설 2(형식/명명)의 상대 우선순위가 올라간다.
