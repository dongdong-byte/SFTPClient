## 0. 유닛의 정의 (한 문장)

> **방화벽류의 조용한 단절로 멈춘 전송을, 유한 시간 안에
> "셧다운과 같은 깨끗한 실패"로 변환한다.**
> 변환 이후는 전부 기존 설계가 받는다 — best-effort 실패 기록,
> 프로세스 종료(lock 해제), 다음 회차 `Recover`·재시도.

- 프로그램은 멈춘 **원인**(방화벽/회선/서버)을 구분할 수 없고, 대응이
  동일하므로 **구분하지 않는다.** 판정 기준은 관측 가능한 사실 하나:
  "정해진 시간 안에 진전이 없다."
- 측위원 mtime 인시던트의 재발 방지가 아니다(그건 유닛 2 몫).
  근거는 §1.1의 코드 취약점 `[확정]` + 신규 리눅스 기관(9/29 설치)의
  통신 불안정 관측 `[관측-미검증]`이다.

## 1. 전제 — 확정 코드 사실 (FOLLOWUP_PLAN v3 §1.1·§1.2)

1. `dialTimeout`(10s)은 TCP+SSH handshake까지만. 직후
   `SetDeadline(time.Time{})`으로 해제 — **전송 중 타임아웃 없음.**
2. `pkg/sftp`의 Write/Stat/Rename은 ctx를 받지 않는다. ctx 취소는
   깃발일 뿐 강제가 아니므로, **블록된 원격 호출은 취소로 풀리지 않고
   호출이 반환될 때까지 끝나지 않는다.** 방화벽이 세션을 조용히 버리면
   Write는 TCP 재전송 한계(십수 분+)까지 블록된다.
3. 블록을 실제로 푸는 유일한 지렛대는 **`ssh.Client.Close()`** —
   연결이 닫히면 대기 중이던 호출이 에러로 반환된다.
4. 연결은 단일 `SFTPFS`(ssh 1 + sftp 1)를 MaxWorkers개 워커가
   **공유**한다. 닫으면 전원이 함께 접힌다.
5. 시작 복구(`internal/put/recovery.go`)는 IN_PROGRESS를 회수한다 —
   원격 `.part` 삭제 + `FailPut`(recoverCause). 실패 기록에 별도
   컨텍스트(`failCtx`)를 쓰는 전례가 이미 있다.
6. 재시도 업로드는 `O_WRONLY|O_CREATE|O_TRUNC`로 원격 `.part`를
   덮어쓴다 — 잔여 `.part`는 재시도 시 자동 재사용된다.
7. lock은 나이 기반 stale 탈취(`LockStaleSeconds`). 살아 있는 프로세스가
   쥐고 있는 한 stale이 아니며, 후속 회차는 `ErrHeld`로 **무경보 정상
   종료(0)** 한다 — 스톨이 셧다운보다 나쁜 이유.

## 2. 전제 — 운영 실측 (2026-09-18, 사용자 제공)

- 최대 파일: RNX3 Daily **2,646KB ≈ 2.6MB** — 대용량 없음.
- 실측 처리량: 3기관 5,000파일 / 45분 ≈ **파일당 0.5초**.
- 신규 리눅스 기관: 40관측소, RNX2+RNX3, Daily+Hourly →
  회차당 최대 약 **440파일 / 1시간 주기**.
- 운영 판단(사용자): 이 규모를 1시간 안에 처리 못 하는 환경이면
  프로그램이 아니라 **장비 부적합**으로 분류한다.

## 3. 설계 — 세 단계

### 3.1 인지: 연결 단위 무진행 (주 감지)

연결 하나에 **`lastProgress` 시각 하나.** 갱신 시점:

- Upload 청크가 실제로 쓰였을 때
- Stat / Rename / Mkdir / Remove 등 원격 호출이 **완료**됐을 때
- SSH keepalive 응답으로는 갱신하지 않는다 (연결 생존 ≠ 작업 진전)

백그라운드 watchdog: **진행 중인 SFTP 작업이 존재하는데** `lastProgress`
가 `StallTimeoutSeconds` 동안 그대로면 무응답으로 판정한다.

**3안 대조 (채택 근거 — 재론 방지):**

| 후보 | 내용 | 판정 |
|---|---|---|
| 파일당 총시간 타임아웃 | 파일 하나가 N초 안에 끝나는가 | `[기각]` 정상 전송을 재는 시계가 아님. 다만 §2 실측상 파일이 소형이라 부작용은 작았을 것 — 기각의 주근거는 아래 연결 단위 안이 같은 효과를 더 싸게 얻기 때문 |
| 작업별 타임아웃 | 원격 호출마다 타이머 래핑 | `[기각]` pkg/sftp가 ctx 미수용이므로 만료 시 종결 수단이 결국 연결 close 하나로 동일. 호출마다 고루틴+타이머 기계를 깔고도 지렛대가 같음. 열거 누락(미래 신규 호출) 위험 |
| **연결 단위 무진행** | lastProgress 하나 + watchdog 하나 | **`[채택]`** 타이머 하나로 같은 지렛대(연결 close)에 도달. 갱신 지점 열거가 누락돼도 다른 호출의 진전이 흡수, 최악은 오탐이 아니라 지연 |

**인정하는 한계:** 한 워커만 멈추고 나머지가 계속 쓰면 즉시 울리지
않는다. 단 이는 미감지가 아니라 **지연 감지**다 — 나머지 워커가 큐를
소진하면 진행 중 작업은 멈춘 것뿐이 되어 lastProgress가 멎고 발화한다.
최악 지연 = 잔여 큐 처리 시간. 방화벽 세션 절단은 통상 전원 동시
정지이므로 1차 목적에는 충분하다.

**`StallTimeoutSeconds` 초안값: 30** (미결 §6-1). 근거: 실측 0.5초/파일
대비 60배 여유. 정상 조건에서 원격 호출 하나가 30초 무응답인 경우는
§2의 운영 판단상 장비/회선 문제로 분류된다. config 키로 노출한다
(신규 기관 현장에서 재빌드 없이 조정 — 프로젝트 관례).

### 3.2 안전망: 회차 전체 상한 (두 겹의 둘째)

`RunDeadlineMinutes`(초안값 50, < 스케줄 주기 60분)를 회차 전체에 건다.
만료 동작은 3.1과 동일한 경로(연결 close → 종료 절차)로 합류한다.

**3.1만으로 안 되는 이유 (복원 근거 — 타 AI 2안 모두 누락):**
3.1의 발화 조건은 "진행 중인 **SFTP** 작업 존재"다. SFTP 밖에서 멈추면
— 설계안 9.3이 허용한 네트워크 저장소(NAS/SMB)상의 스캔·해시·로컬
read 블록 등 — watchdog은 영원히 침묵하고 lock을 쥔 좀비가 재발한다.
회차 상한은 열거 불가능한 블록 지점 전부를 덮는 **불변식**이다:
"무슨 일이 있어도 다음 회차 전에 끝난다." 이 불변식이 있어야
"lock 장기 점유·회차 겹침이 구조적으로 불가능"이 참이 된다.
구현 비용은 타이머 하나.

### 3.3 회차 종료: 닫기 → 기존 실패 경로 → 프로세스 종료

발화(3.1 또는 3.2) 시 순서 — **순서가 계약이다:**

1. **신규 착수 중단** — pool 취소. 이후 BeginPut 없음
   (attempts 소모는 그 순간 전송 중이던 최대 MaxWorkers개로 한정).
2. **연결 close** — `ssh.Client.Close()`. 블록된 호출들이 에러로 반환.
   **정리(Remove 등)보다 close가 먼저다** — 죽은 연결로 cleanup
   (30초 타임아웃)을 먼저 돌리면 종료가 30초×건수로 늘어난다.
3. **best-effort 실패 기록** — 이미 BeginPut된 항목을 `failOne`으로
   FAILED(원인: stall timeout) 시도. 원격 `.part` Remove는 실패해도
   무방(§1-6 덮어쓰기). 기록에는 회차 ctx가 아닌 **독립 단수명 ctx**
   사용(§1-5 `failCtx` 전례 재사용).
4. **프로세스 종료** — Transfer/main return → `defer` lock 해제,
   비정상 종료 코드로 회차 마감.
5. **다음 정시** — lock → `Recover`(3에서 기록 실패해 IN_PROGRESS로
   남은 항목을 여기서 접음: 원격 `.part` 삭제 + FAILED) → 스캔 →
   FAILED 재시도.

> **성공 조건의 재정의:** 이번 회차에 FailPut이 반드시 성공하는 것이
> 아니라 **프로세스가 반드시 끝나는 것**이다. 기록은 최선을 다하고,
> 못 하면 Recover가 받는다. 새 상태기계·새 복구 절차를 만들지 않는다.

VERIFIED 확정분은 건드리지 않는다(회차 부분 성공 보존 — 기존 ledger
설계가 이미 보장).

## 4. attempts 예산 — 현행 유지 `[권고]`

**결정: 소진 규칙(`FAILED && attempts >= MaxRetries` → 자동 제외) 무변경.**
유닛 3은 예산 정책을 바꾸지 않고 두 가지만 한다:

- **소모 축소:** 3.3-1의 착수 차단으로 스톨 회차의 예산 소모를
  최대 MaxWorkers개로 한정.
- **소진 가시화:** 기존 exhausted WARN·집계 유지. 임계 경보 승격은
  유닛 4 범위. **소진 파일의 운영자 수동 재개 절차를 문서로 확정하는
  것이 본 권고의 성립 조건이다** (없으면 "조용한 포기"와 구별 불가).

**산술 근거:** 파일당 0.5초·1시간 주기에서 죄 없는 파일이 소진(예:
5회)에 도달하려면 그 파일 전송 순간의 단절이 5개 회차에서 반복되어야
한다. 그런 환경은 사용자 판정대로 "프로그램 대응 범위 밖의 인프라
고장"이며, 이때 소진은 결함이 아니라 **시끄러운 고장 신호**다.

**기각 2건 (재론 방지):**

- `[기각]` 소진 폐지 + 회차당 재시도 상한·선정 순서(타 AI 1안):
  후보 선정의 밑돌 교체 + 새 스케줄링 정책(MaxFilesPerRun·세트
  경계와 상호작용) + 반복 실패가 고장 신호를 흡수 + 회귀 범위 과대.
  "수정 최소" 원칙(사용자 확정) 위반.
- `[기각]` 자기 유발 실패(watchdog이 끊어서 실패한 작업)만 예산 미소모:
  원인 추측이 아닌 자기 행위라 관측 가능하다는 장점은 있으나,
  attempts는 **BeginPut 시점에 이미 증가**하므로 미소모 구현은 차감을
  요구하고, v2 §6.8이 "단순 차감·초기화를 확정안으로 삼지 않는다"로
  배제했다.

**경계 명기:** MaxRetries 회차 연속 단절, 실패 파일의 스캔 범위(Deep
30일) 이탈은 프로그램 대응 범위 밖의 인프라 문제로 분류한다.

## 6. 미결 — 교차검증과 함께 확정할 항목

1. **`StallTimeoutSeconds` 값** — 초안 30초. 장애 재현 테스트(방화벽
   시뮬레이션: iptables DROP 등)와 작업별 실측으로 검증 후 확정.
2. **회차 상한의 최후 수단(3단) 여부** — 상한 만료 → close 후에도
   유예(예: +60초) 안에 프로세스가 안 끝나는 극단(OS 수준 블록,
   미지의 비SFTP 블록)에서 무조건 종료(`os.Exit`)를 둘 것인가.
   찬성 근거: 프로세스가 죽으면 셧다운 복구 경로(Recover + stale
   lock)가 받아줌이 확정돼 있어 안전, "구조적으로 불가능" 문장이
   이것으로 완성됨. 반대 근거: defer를 건너뛰는 강제 종료의 거칢.
3. **`RunDeadlineMinutes` 값** — 초안 50분. 440파일 실측(≈4분) 대비
   10배 이상 여유. Deep Scan 회차의 소요와 함께 검증.

## 7. 검증 계획 (초안)

1. 단위: watchdog 발화 조건(진행 중 작업 존재 + 무진행 N초),
   lastProgress 갱신 지점, 발화 시 close 호출.
2. 장애 재현 E2E: 로컬 SFTPGo + 전송 중 패킷 차단(iptables DROP /
   네트워크 차단) → N초 내 발화 → 프로세스 종료 → 재실행에서
   Recover·재시도·최종 성공 확인. RST(시끄러운 끊김)와 DROP(조용한
   끊김)을 구분해 각각 검증.
3. 무영향 회귀: 정상 대량 전송(BNC 15분 생성 환경)에서 watchdog
   무발화·처리량 무저하 확인.
4. 회차 상한: 인위적 지연 주입으로 상한 발화 → lock 해제 →
   다음 회차 정상 확인.
