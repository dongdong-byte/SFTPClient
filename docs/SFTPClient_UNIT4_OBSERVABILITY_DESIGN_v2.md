## 0. 목적

내용 변경으로 전송 대상으로 분류한 건수와, 내용은 같아서 mtime 변경에
따른 revision 증가를 억제한 건수를 구분해 회차별로 남긴다.
자동 재시도에서 소진으로 제외된 파일은 즉시 WARN으로 알린다.

400건 같은 임의의 절대 문턱은 채택하지 않는다. 정상 분포를 아직
측정하지 않았으므로 suppressed·content_changed의 크기만으로 이상을 선언하지 않는다.

## 0.1 코드 대조 — 이미 있는 것과 없는 것 `[코드]`

초안 작성 시 HEAD와 대조했다. 신규 작업 범위가 좁다는 사실이 이 절의 요지다.

**이미 있다 (재사용·확장 대상, 새로 만들지 않는다):**

- 회차별 카테고리 집계 줄 — `internal/put/plan.go` `RunReport.Print`가
  `unchanged / new / changed / metadata_only`를 이미 출력한다.
  §2가 세려는 값의 카운터가 전부 여기 있다.
- 해시 계측 줄 — `hash new/changed/drift/backfill … failed/unstable/deferred`.
  §2.2가 "함께 볼 수 있게 한다"고 한 값들이다.
- 소진 WARN — `internal/put/runner.go`의 `ExcludedExhausted` 집계와
  `[PUT][WARN] category=… exhausted=… (MaxRetries=…): 예시` 출력.
  예시 상한 5(`exhaustedExampleCap`)까지 §6의 요구와 일치한다.
- dry-run 구분 — 로그 태그가 `[PUT]` / `[DRYRUN]`로 갈린다.
  `RunReport`가 실제로 들고 있는 실행 구분은 `DryRun`뿐이다
  (`internal/put/type.go`). `SeedMode`와 Hot/Deep 범위는 리포트에 없고
  `Print`도 모른다.

**없다 (이번 유닛의 실제 신규 작업):**

1. `evaluated`와 `suppressed_ratio` — §3의 정의로 계산해 기존 줄에 붙인다.
2. **seed 회차의 구분** — seed도 `Print` 태그가 `[PUT]`이라 live 집계와
   섞인다. `main`은 `RunOptions.SeedMode`로 경로를 가르지만 그 사실이
   요약 줄까지 전달되지 않는다. §4의 "seed는 정상 live 분포와 섞지 않는다"가
   현재 로그로는 성립하지 않는다.
3. **Hot/Deep 범위의 구분** — Deep일 때만 `main`이 별도 `[SCAN] deep run`
   줄을 남긴다. `Run`/`Print`는 `scan.Range`만 받고 창의 이름(hot/deep)은
   모른다. 요약 줄만 보면 어느 스캔 창이었는지 알 수 없어 §5의 "범위를
   연결할 수 있어야 한다"가 성립하지 않는다.

2·3은 배포 후 로그를 모아 분포를 볼 때 **분석 자체를 무효로 만드는** 결함이다
(다른 모집단이 한 통에 섞인다). 그래서 이번 범위에 포함한다.

## 1. 합의한 두 단계

1. 이번 유닛: 회차별 INFO 집계에 절대 건수와 suppressed 비율을 남기고,
   **그 회차가 어떤 모집단인지(live/dry-run/seed, Hot/Deep)를 같은 줄에서
   식별할 수 있게** 한다. exhausted가 1건 이상이면 WARN을 남긴다.
   새 임계 설정과 회차 간 상태 저장은 없다.
2. 배포 후: 기관별·스캔 모드별 로그를 수집하고 정상 운영 구간을 확인한다.
   그 후 기관별 설정 문턱의 필요성과 값을 별도로 결정한다.

관측 기간과 배포일은 이 초안에서 새로 확정하지 않는다. 몇 주 또는 p95는
분석 방법의 예시이며, 특정 기간이나 백분위만으로 경보 기준이 자동 결정되지는 않는다.

## 2. 무엇을 세는가

### 2.1 단위: 파일-회차

집계 단위는 관측소나 상류의 touch 횟수가 아니라, 한 회차에서 판정한
파일 식별자(category + 정규화 이름)다. 같은 식별자의 중복 관측은 기존
중복 제거 규칙을 따른다. 한 파일이 회차 사이에 여러 번 갱신되어도
이번 관측에서는 한 번만 센다.

`mtime_drift_suppressed` 1건은 size가 같고 mtime이 다르며 저장된 지문과
현재 지문이 같아, mtime 변경에 따른 revision 증가를 억제한 판정 1건이다.
현재 코드의 `CategoryReport.MetadataOnly`에 대응한다.

이 값은 “비정상 갱신 확정”이나 “전송 한 건 절약의 확정치”가 아니다.
정당한 복사 작업도 해당할 수 있고, 기존 FAILED/PENDING 상태 때문에
같은 revision의 전송 후보가 되는 것은 별개다.

### 2.2 content_changed의 해석

현재 `CategoryReport.Changed`는 내용 변경으로 **분류한** 건수다.
지문 차이뿐 아니라 기존 지문 부재·판정 해시 읽기 실패로 보수적으로
변경 취급한 경우도 포함한다. 이를 모두 “실제 바이트 변경을 확인했다”고
설명하지 않는다. 신규 파일은 `New`이며 content_changed와 구분한다.

최소 구현에서는 이 기존 의미를 유지하고 `hash_failed`, `hash_unstable`,
백필 관련 기존 계측을 함께 볼 수 있게 한다. 확인된 변경과 보수 판정의
세분화가 필요하면 별도 후속으로 결정한다.

## 3. 비율의 분모

사용자 합의의 “관측 후보”는 실제 전송 후보가 아니라 **변경 판정 모집단**을
뜻한다. 로그에서는 혼동을 피하려고 `evaluated`라고 표기한다.

- 초안 정의: `evaluated = Unchanged + New + Changed + MetadataOnly`.
  네 값은 이미 `CategoryReport`에 있다. **새 증가 카운터를 두지 않고**
  `Print` 시점에 합산한다. 판정 루프에 다섯 번째 계수를 깔면 다음
  분기 추가에서 분모만 조용히 어긋난다.
- `suppressed_ratio = MetadataOnly / evaluated`.
- 분모가 0이면 비율은 `n/a`로 표시한다. 정상 0%로 해석시키지 않는다.
- 실제 전송 `Candidates`, `TotalCandidates`, MaxFilesPerRun 절단 후 건수를
  분모로 쓰지 않는다. 억제된 파일은 전송 후보에서 빠질 수 있기 때문이다.
- 임시 파일·Ingress 거부·중복·hash unstable 등 판정에 도달하지 못한 입력은
  분모에 포함하지 않는다. unstable은 해시 줄의 `unstable=`로 본다.
  분모에서 뺐다고 그 파일이 사라지는 것은 아니다.

**가장자리 `[코드]`:** `MetadataOnly++` 뒤에 `TouchCommonMTime`이 0행이면
그 파일은 이번 집계의 suppressed에 들어가고, 기준선 mtime은 옮기지 않은 채
회차에서 빠진다(`runner.go`). 다음 live 회차에 같은 드리프트를 다시 해시한다.
집계와 기준선이 한 회차 어긋날 수 있다. 이번 유닛에서 카운터를 되돌리거나
판정 순서를 바꾸지 않는다. 비율을 읽을 때 이 경로가 있다는 것만 안다.

카테고리별 값을 기본으로 남긴다. 전체 비율을 추가한다면 비율의 산술평균이
아니라 분자 합계 / 분모 합계로 계산한다. 중도 오류의 집계는 완결 회차와 구별한다.

## 4. 매시간 갱신은 어떻게 보이는가

저장 지문이 있고 안정적으로 해시할 수 있으며 스캔·Grace 조건을 통과한
파일은 다음 경로로 반복 관측할 수 있다.

1. 상류가 mtime을 변경한다.
2. 이번 live 회차가 내용 동일을 확인하고 suppressed를 센다.
3. 장부 mtime 기준선을 현재 값으로 갱신한다.
4. 다음 회차 전에 mtime이 다시 바뀌면 다음 회차에서도 같은 판정을 할 수 있다.

주기성 감지기는 만들지 않는다. 회차별 로그의 반복을 운영자가 확인한다.
dry-run은 기준선을 갱신하지 않으므로, 같은 사건이 반복 계수될 수 있다.
seed는 지문 판정 경로가 다르므로 정상 live 분포와 섞지 않는다.

몇 회차에서 비슷한 수가 보인다는 사실은 지속 갱신의 단서이지, 매시간
상류 작업이 실행됐다는 증명은 아니다. Grace 보류·스캔 창 이동·백필·오류도
분포를 바꾼다. 세 회차만으로 원인을 확정하지 않는다.

## 5. 로그 정책

완결된 live 회차에는 0건도 포함해 카테고리별 INFO 요약을 남긴다.

**새 줄을 추가하지 않는다.** §0.1이 확인한 대로 기존 `RunReport.Print`의
카테고리 요약 줄이 같은 사실을 이미 담고 있다. 새 `[DRIFT]` 줄을 만들면
같은 사실의 출처가 둘이 되고, 둘이 어긋나는 날이 온다. 기존 줄을 확장한다.

확장 후의 모습(수치는 형식 설명용이며 정상치나 경보 문턱이 아니다):

```text
[PUT] mode=live range=deep category=... dirs=.. missing=.. listed=.. errs=..
      unchanged=.. new=.. changed=.. metadata_only=.. evaluated=100 suppressed_ratio=20.0%
```

- `mode` — live / dryrun / seed. 기존 태그(`[PUT]`·`[DRYRUN]`)만으로는
  seed가 live와 구별되지 않으므로 필요하다(§0.1-2).
- `range` — hot / deep. 어느 스캔 창의 모집단인지가 분포 해석의 전제다(§0.1-3).
- 표기 위치(태그로 할지 필드로 할지)와, `SeedMode`·스캔 창 이름을
  `Print`까지 어떤 필드로 실어 보낼지는 구현이 정한다. 요구는 "요약 줄
  하나만 보고도 모집단을 식별할 수 있을 것"이다. 식별용 값을 위해
  판정·장부 쓰기를 바꾸지 않는다.

중도 실패 시 출력 가능한 집계는 `partial`임을 명시하거나 기존 실패 로그로
불완결임을 구분한다. 요약 누락을 0건으로 취급하지 않는다.

로그는 사람이 조회할 관측 수단이다. INFO 각인만으로 자동 알림이나
운영자의 확인을 보장한다고 표현하지 않는다. 큰 suppressed·content_changed
건수나 비율을 이유로 이번 단계에서 WARN으로 승격하지 않는다.

## 6. exhausted는 즉시 WARN

현재 revision이 FAILED이고 attempts가 상한에 도달해 **실제 자동 후보에서
제외된** 파일이 1건 이상이면 WARN 대상이다. 분포 학습이 필요 없다.

**이 경로는 이미 구현되어 있다 `[코드]`** — `internal/put/runner.go`의
`ExcludedExhausted` 집계, `exhaustedExampleCap`(5) 제한 예시,
`[PUT][WARN] category=… exhausted=… (MaxRetries=…): 예시 외 N건` 출력.
이번 작업은 **새로 만드는 것이 아니라 이 동작을 검증하고 회귀 테스트로
고정하는 것**이다. 같은 사건의 경고를 중복 생성하지 않는다.

- 건수·카테고리·MaxRetries·제한된 예시로 조치 대상을 식별한다.
- 회차별 재경고는 허용한다. 회차 간 중복 경고 억제 상태를 저장하지 않는다.
- 이 수는 이번 스캔에서 확인한 소진 제외 건수다. DB 전체 소진 잔량이나
  스캔 범위를 벗어난 미전송 파일 수를 보장하지 않는다.
- 경고를 내는 것과 재시도 기회를 복구하는 것은 별개다. attempts 초기화,
  revision 변경, resend 의미론은 이번 유닛에서 바꾸지 않는다.

## 7. 운영 가설과 아직 모르는 것

- 측위원의 반복 mtime 갱신 때문에 suppressed가 매 회차 많이 나올 수 있다는
  것은 예상이다. 유닛 2 배포 후 실측으로 확인한다.
- 다른 기관의 정상 suppressed가 0 근처일 것이라는 것도 가설이다.
- “거의 0 또는 거의 전수인 쌍봉 분포”는 아직 입증되지 않았다.
- 110관측소 × 약 50파일 = 약 5,500건은 가정에 따른 설명용 계산이다.
  실제 카테고리·파일 종류·스캔 창·생성 시점·거부 조건에 따라 달라진다.
- 비율은 기관 규모 비교를 돕지만 Hot/Deep, 신규 유입량, 지문 백필 정도가
  다른 회차를 동일한 정상 분포로 만들지는 않는다.

## 8. 이번에 하지 않는 것

- suppressed·content_changed의 절대치/비율 임계 및 기관별 경보 설정.
- 주기성·연속 N회·자동 정상 분포 학습, DB 스키마 변경.
- 스캔·후보 선정·해시·revision·전송·재시도 정책 변경.
- 유닛 3의 timeout 재설계. 기존 STALL 로그와 비정상 종료는 유지한다.
- lock 생존 감시, .part/.filepart 계측 분리, 메일 등 외부 알림 추가.

|---|---|---|
| UNIT3 v3 §3.7 | 연속 스톨 N회의 경보화. stall 계측을 기존 집계에 추가 | 하지 않는다. 스톨 자체가 아직 현장 관측이 없다(UNIT3 §1). `[STALL]` WARN + 비정상 종료 코드로 회차 단위 가시화는 이미 되어 있다 |
| FOLLOWUP v3 §6.4 | `lock.ErrHeld` 무경보 정상 종료 — 장기 점유에 신호가 없다 | 하지 않는다. 유닛 3의 조기 자체 종료로 장기 점유의 주 원인이 줄었다. 그래도 남는지를 배포 후 로그로 먼저 본다 |
| UNIT5 §3 | 버려진 `.filepart`의 장기 잔류 경보 | 하지 않는다. `SkippedPart`가 매 회차 찍히므로 신호는 있다 |
| UNIT3 v3 §3.7·§6-6 | 소진 파일의 운영자 재개(`resend`) 의미론 | 유닛 4의 소유가 아니다. exhausted WARN은 "알린다"까지이며 "복구한다"는 별개다(§6) |

## 9. 구현 시 최소 확인 항목

1. 억제·변경·신규·불변의 집계가 서로 중복되지 않고 분모와 일치하는가.
   **사람의 확인이 아니라 테스트로 고정한다** — `evaluated`가
   `Unchanged + New + Changed + MetadataOnly`와 같고, 판정에 도달하지 못한
   입력(Ingress 거부·중복·hash unstable·임시 파일)이 분모 밖에 있음을
   회귀 테스트가 지킨다. 합산은 Print(또는 그와 같은 순수 함수)에서
   이루어져야 판정 루프와 분모가 따로 놀지 않는다.
2. 0건, 분모 0, 중도 실패가 구별되는가. **dry-run·seed·Hot/Deep이 요약 줄
   하나로 식별되는가**(§5 — 이번에 새로 넣는 부분이므로 테스트 대상이다).
3. 세트 보류·전송 절단·재시도 후보 수가 suppressed 비율을 왜곡하지 않는가.
4. exhausted 1건 이상이면 기존 WARN이 나오고 예시는 제한되는가
   (기존 동작의 회귀 고정, §6).
5. 로그 변경이 후보 선정·장부·전송 동작을 바꾸지 않는가.

분모가 0인 회차는 정상 0%가 아니라 **스캔이 아무것도 보지 못했다는 신호**로
읽는다. 같은 줄의 `dirs/missing/listed/errs`와 함께 본다.

초안 작성 단계에서는 코드를 수정하거나 위 검증을 실행하지 않는다.
